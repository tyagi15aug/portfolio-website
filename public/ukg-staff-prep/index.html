Chapter 01

Kubernetes and EKS from zero

A container is a box that holds one app and everything the app needs. Kubernetes is a system that runs many containers on many machines for you. You write the result that you want, for example "keep 3 copies of my app alive". Kubernetes then works all the time to make the real state match your wish. Think of a large restaurant kitchen. You give the head chef the menu and the number of plates. The head chef gives the work to the cooks and replaces a cook who goes home sick. EKS is Kubernetes that AWS operates for you, so you do not manage the "head chef" machines.

1. Containers and the main idea of Kubernetes

Container image
Idea

An image is a frozen package of an app, its runtime and its libraries. You build it one time and run it anywhere.

Example

A Docker image for a Node.js results API contains Node 20, node_modules and the app code.

Term

A container image is an immutable, layered file system plus metadata (OCI format). A tag such as :3f2c1ab points to a digest such as sha256:.... The digest never changes.

Container
Idea

A container is one running copy of an image. It is isolated from other containers, but it shares the kernel of the machine.

Example

Three containers from the same image give three copies of the results API.

Term

A container is a process that uses Linux namespaces for isolation and cgroups for CPU and memory limits.

Container registry
Idea

A registry is a store for images. Machines pull images from it before they start containers.

Example

The CI job pushes results-api:3f2c1ab to Amazon ECR. The cluster pulls it from ECR.

Term

Amazon ECR is the AWS registry. Docker Hub is a public registry with pull rate limits.

Declarative desired state
Idea

You tell Kubernetes what you want, not the steps to get it. Kubernetes finds the difference and fixes it.

Example

You write replicas: 3. One pod dies. Kubernetes sees 2 and starts a new pod.

Term

This is the reconciliation loop. Controllers compare the desired state (spec) with the observed state (status) and act to remove the difference.

Manifest (YAML)
Idea

A manifest is a YAML file that describes one or more Kubernetes objects.

Example

kubectl apply -f deploy.yaml sends the file to the cluster.

Term

Each object has apiVersion, kind, metadata (name, namespace, labels) and spec. Kubernetes adds status.

2. The cluster: control plane, worker nodes, and what EKS runs for you

Cluster
Idea

A cluster is a group of machines that Kubernetes controls as one system.

Example

The UKG test platform can have one EKS cluster with 50 machines.

Term

A cluster has a control plane (the brain) and worker nodes (the muscle).

Control plane
Idea

The control plane makes all decisions. It does not run your app containers.

Example

When you ask for 3 pods, the control plane decides where they go.

Term

The control plane contains the API server, etcd, the scheduler and the controller manager.

API server
Idea

The API server is the front door of the cluster. Every tool and every component talks to it.

Example

kubectl get pods sends an HTTPS request to the API server.

Term

kube-apiserver checks authentication, RBAC and admission rules, then stores objects in etcd.

etcd
Idea

etcd is the memory of the cluster. It stores every object and its state.

Example

Your Deployment YAML lives in etcd after you apply it.

Term

etcd is a distributed, consistent key-value store. Only the API server talks to it.

Scheduler
Idea

The scheduler picks a node for each new pod.

Example

A pod asks for 2 CPU. The scheduler skips nodes with less than 2 free CPU.

Term

kube-scheduler filters nodes (requests, taints, affinity) and then scores them. A pod with no fit stays Pending.

Controller manager
Idea

The controller manager runs many small loops. Each loop keeps one kind of object correct.

Example

The ReplicaSet controller sees 2 pods instead of 3 and makes a new pod.

Term

kube-controller-manager runs the Deployment, ReplicaSet, Job, Node and EndpointSlice controllers, and others.

Worker node
Idea

A worker node is a machine that runs your pods.

Example

On EKS, a worker node is usually an EC2 instance, for example m6i.xlarge.

Term

Each node runs the kubelet, kube-proxy and a container runtime.

kubelet
Idea

The kubelet is the agent on each node. It starts the containers and reports their health.

Example

The kubelet runs the liveness probe and restarts a container that fails it.

Term

The kubelet watches the API server for pods bound to its node. It also reports node conditions such as Ready and MemoryPressure.

kube-proxy
Idea

kube-proxy makes the Service IP work on each node. It sends Service traffic to a pod.

Example

A call to results-api:80 goes to one of the 3 ready pods.

Term

kube-proxy programs iptables or IPVS rules from EndpointSlices. On EKS it runs as a DaemonSet add-on.

Container runtime
Idea

The container runtime is the program that really runs containers on the node.

Example

On EKS nodes, the runtime is containerd.

Term

The kubelet talks to the runtime through the CRI (Container Runtime Interface). Docker is no longer the runtime.

Amazon EKS
Idea

With EKS, AWS runs the control plane for you. You only run or rent the worker nodes.

Example

You never log in to the API server machines. AWS patches them and makes them highly available.

Term

EKS gives a managed, multi-AZ control plane with an endpoint that can be public, private or both. You pay per cluster hour plus the nodes.

Managed node group
Idea

A managed node group is a group of EC2 nodes that EKS creates and updates for you.

Example

You ask for 3 to 10 m6i.xlarge nodes. EKS makes an Auto Scaling group and drains nodes during upgrades.

Term

A managed node group uses an EC2 Auto Scaling group and an EKS-optimized AMI. It supports On-Demand and Spot.

Self-managed nodes
Idea

Self-managed nodes are EC2 instances that you create and join to the cluster yourself.

Example

A team needs a special AMI with GPU drivers, so it builds its own Auto Scaling group.

Term

You own the AMI, the upgrades and the drain process. This gives full control but more work.

AWS Fargate
Idea

Fargate runs each pod without a node that you can see. AWS gives the machine.

Example

A small cron job runs on Fargate, so no team must patch a node for it.

Term

A Fargate profile selects pods by namespace and labels. Limits: no DaemonSets, no privileged pods, and pod start is slower.

Karpenter (as a node option)
Idea

Karpenter adds the right EC2 node fast when pods cannot find a place.

Example

50 browser pods are Pending. Karpenter starts two large Spot nodes in about a minute.

Term

Karpenter is an open-source node autoscaler, v1 GA. It uses NodePool and EC2NodeClass objects and calls EC2 directly, without node groups.

EKS add-ons
Idea

Add-ons are cluster parts that AWS can install and upgrade for you.

Example

VPC CNI, CoreDNS, kube-proxy and the Pod Identity agent are add-ons.

Term

EKS add-ons have versions that you upgrade with the cluster. The AWS Load Balancer Controller is usually installed with Helm.

3. Workloads: pods and the objects that manage them

Pod
Idea

A pod is the smallest thing Kubernetes runs. It wraps one container or a few containers that must live together.

Example

A pod has the app container and a small log-shipper sidecar. Both share localhost.

Term

All containers in a pod share one IP address, one network namespace and the pod volumes. Pods are disposable: a new pod gets a new IP.

Labels and selectors
Idea

A label is a tag on an object. A selector is a query that finds objects by tag.

Example

Pods have app: results-api. The Service selects app: results-api to find them.

Term

Labels are key-value pairs in metadata.labels. Deployments, Services, NetworkPolicies and PDBs all find pods by selector. A typo breaks the link without an error.

ReplicaSet
Idea

A ReplicaSet keeps an exact number of identical pods alive.

Example

The ReplicaSet wants 3 pods. A node dies with one pod. The ReplicaSet makes a new pod on another node.

Term

You almost never create a ReplicaSet directly. A Deployment creates one ReplicaSet per version of the pod template.

Deployment
Idea

A Deployment runs a stateless app and changes versions safely.

Example

You change the image tag. The Deployment starts new pods and stops old pods step by step.

Term

Deployment → ReplicaSet → Pods. A rolling update makes a new ReplicaSet and scales it up while the old one scales down. kubectl rollout undo goes back to the previous ReplicaSet.

StatefulSet
Idea

A StatefulSet runs apps that need a stable name and their own disk.

Example

A 3-node database cluster: db-0, db-1, db-2, each with its own volume.

Term

StatefulSet pods get ordinal names, stable DNS names (through a headless Service) and one PersistentVolumeClaim each. They start and stop in order.

DaemonSet
Idea

A DaemonSet runs one copy of a pod on every node.

Example

A log agent (Fluent Bit) must run on each node to read container logs.

Term

When a node joins, the DaemonSet adds the pod. kube-proxy and the VPC CNI (aws-node) are DaemonSets.

Job
Idea

A Job runs pods until the task completes, then stops.

Example

A Job runs one Playwright shard and exits with code 0 when the tests pass.

Term

A Job has completions, parallelism, backoffLimit and activeDeadlineSeconds. ttlSecondsAfterFinished deletes old Jobs.

CronJob
Idea

A CronJob makes a Job on a schedule.

Example

A CronJob at 02:00 every night runs a test-data cleanup.

Term

A CronJob uses cron syntax in schedule. concurrencyPolicy: Forbid stops a new run while the last one still runs.

4. Networking inside the cluster: Services

Service
Idea

Pod IPs change all the time. A Service gives one stable name and IP in front of a group of pods.

Example

Other pods call http://results-api.test-platform and never need a pod IP.

Term

A Service selects pods by label and load-balances across the ready ones. CoreDNS gives it the name <service>.<namespace>.svc.cluster.local.

ClusterIP
Idea

ClusterIP is the default Service type. Only code inside the cluster can reach it.

Example

The Selenium hub calls the session store through a ClusterIP Service.

Term

type: ClusterIP gives a virtual IP that exists only in kube-proxy rules. It is not reachable from the VPC.

NodePort
Idea

NodePort opens the same port on every node. Traffic to that port on any node reaches the Service.

Example

Port 31080 on every node forwards to results-api.

Term

type: NodePort uses a port from 30000 to 32767. It is a building block for the instance target type of a load balancer.

LoadBalancer
Idea

A LoadBalancer Service asks the cloud for a real load balancer in front of the Service.

Example

On EKS, a LoadBalancer Service gets an NLB for TCP traffic, for example a gRPC test-results ingest.

Term

With the AWS Load Balancer Controller, type: LoadBalancer creates an NLB. Use annotations such as service.beta.kubernetes.io/aws-load-balancer-type: external.

port and targetPort
Idea

port is the number that callers use on the Service. targetPort is the number that the container listens on.

Example

Callers use port 80. The container listens on 8080. So port: 80, targetPort: 8080.

Term

A wrong targetPort gives connection refused or a 503, even when pods are healthy.

Endpoints and EndpointSlices
Idea

An EndpointSlice is the live list of ready pod IPs behind a Service.

Example

kubectl get endpointslices -l kubernetes.io/service-name=results-api shows 3 IPs. An empty list means no pod is ready or the selector is wrong.

Term

The EndpointSlice controller fills the list from the selector and the readiness state. EndpointSlices replaced the older Endpoints object for scale.

CoreDNS
Idea

CoreDNS is the DNS server inside the cluster. It turns Service names into IPs.

Example

A pod resolves results-api.test-platform to the ClusterIP.

Term

CoreDNS runs as a Deployment in kube-system. Many DNS failures in tests come from a CoreDNS overload.

Amazon VPC CNI
Idea

On EKS, each pod gets a real IP address from your VPC subnet.

Example

A pod has IP 10.0.12.45. An ALB in the same VPC can send packets straight to it.

Term

The VPC CNI plugin (aws-node DaemonSet) attaches ENIs and secondary IPs to nodes. Pods per node are limited by ENIs and IPs, unless you turn on prefix delegation.

5. Traffic from outside: Ingress and AWS load balancers

Ingress
Idea

An Ingress is a set of HTTP routing rules from outside the cluster to Services.

Example

results.example.com/ goes to results-api. results.example.com/grid goes to selenium-hub.

Term

An Ingress object is only rules. It does nothing without an Ingress controller. ingressClassName picks the controller.

Ingress controller
Idea

An Ingress controller reads Ingress rules and makes a real proxy or load balancer obey them.

Example

ingress-nginx runs NGINX pods. The AWS Load Balancer Controller makes an AWS ALB. The community ingress-nginx project is retired since March 2026, so use the AWS Load Balancer Controller or Gateway API for new work.

Term

Different controllers give different behavior. A 503 can come from the controller itself when it has no ready backends.

AWS Load Balancer Controller
Idea

This controller turns Kubernetes objects into AWS load balancers.

Example

You apply an Ingress with ingressClassName: alb. An ALB appears in the AWS console a few minutes later.

Term

It creates an ALB for an Ingress and an NLB for a Service of type: LoadBalancer. It needs IAM permissions through IRSA or Pod Identity.

ALB and NLB
Idea

An ALB understands HTTP. An NLB only moves TCP or UDP packets very fast.

Example

Use an ALB for a web dashboard with host and path rules. Use an NLB for a raw TCP or gRPC endpoint with static IPs.

Term

ALB is Layer 7: TLS end, host/path rules, HTTP health checks. NLB is Layer 4: very low latency, static IPs, preserves the client IP.

Target group
Idea

A target group is the list of places that the load balancer sends traffic to. It also checks their health.

Example

The target group for results-api holds 3 pod IPs on port 8080.

Term

Each target group has a protocol, port and health check (path, port, healthy and unhealthy thresholds). Only healthy targets get traffic.

Target type ip vs instance
Idea

With ip, the load balancer sends traffic straight to pod IPs. With instance, it sends traffic to a NodePort on each node.

Example

ip mode: ALB → pod. instance mode: ALB → node:31080 → kube-proxy → pod, maybe on another node.

Term

ip needs the VPC CNI and is required for Fargate. It removes one network hop and gives better health checks. Set it with alb.ingress.kubernetes.io/target-type: ip.

Deregistration delay
Idea

When a pod leaves the target group, the ALB waits a while before it closes connections to that pod.

Example

The default wait is 300 seconds. Open requests can finish in that time.

Term

This is deregistration_delay.timeout_seconds. It must fit with the pod terminationGracePeriodSeconds and the preStop hook, or requests fail during deploys.

6. Pod lifecycle: the states you see in kubectl get pods

Pending
Idea

The pod exists, but it does not run yet.

Example

No node has 4 free CPU, so the pod waits. kubectl describe pod shows 0/5 nodes are available: insufficient cpu.

Term

Common causes: insufficient resources, taints, no free pod IPs, a PersistentVolumeClaim not bound, or a slow image pull.

Running
Idea

At least one container in the pod has started. This does not mean that the app works.

Example

The pod is Running, but the app still loads its cache and fails readiness.

Term

Running is a pod phase. The READY column (for example 0/1) tells you about readiness.

Running is not Ready
Idea

Running means the process is alive. Ready means the pod passes the readiness probe and can get traffic.

Example

kubectl get pods shows results-api-x 0/1 Running. The Service sends it no requests.

Term

The Ready condition comes from the readiness probe. Only Ready pods are in the EndpointSlices of a Service.

Succeeded and Failed
Idea

Succeeded means that all containers exited with code 0. Failed means at least one container exited with an error and will not restart.

Example

A Playwright Job pod ends Completed (Succeeded) or Error (Failed).

Term

These phases apply to pods with restartPolicy: Never or OnFailure, which Jobs use.

CrashLoopBackOff
Idea

The container starts, crashes, and starts again. Kubernetes waits longer before each new restart.

Example

A missing env var makes the app exit at start. The wait grows 10s, 20s, 40s, up to 5 minutes.

Term

This is a waiting reason, not a phase. Use kubectl logs <pod> --previous to see the log of the crashed container.

ImagePullBackOff and ErrImagePull
Idea

The node cannot download the image.

Example

The tag results-api:3f2c1ab does not exist in ECR, or the node role has no ECR pull permission.

Term

Causes: wrong name or tag, missing registry credentials, network path to the registry, or Docker Hub rate limits.

OOMKilled
Idea

The container used more memory than its limit. The kernel killed it.

Example

A Chrome browser pod with a 1Gi limit opens a big page and dies.

Term

The last state shows Reason: OOMKilled, Exit Code: 137. 137 = 128 + 9 (SIGKILL). A process can get SIGKILL for other reasons too, so read the reason.

CreateContainerConfigError
Idea

Kubernetes cannot build the container settings.

Example

The pod uses secretKeyRef key db-pass, but the Secret has db-password.

Term

Typical causes are a missing ConfigMap, Secret or key. kubectl describe pod shows the exact name in Events.

7. Probes: how Kubernetes knows that your app is healthy

Liveness probe
Idea

The liveness probe asks: "Are you stuck?" If the answer is no too many times, the kubelet restarts the container.

Example

The app deadlocks. /healthz stops answering. The kubelet restarts the container after 3 failures.

Term

livenessProbe with httpGet, tcpSocket, exec or grpc. Danger: a liveness probe that checks a database restarts all pods when the database is slow.

Readiness probe
Idea

The readiness probe asks: "Can you take traffic now?" If not, the pod gets no traffic, but it is not restarted.

Example

The app warms a cache for 20 seconds. Readiness fails, so the Service sends no requests until the cache is ready.

Term

A failed readinessProbe sets Ready=False and removes the pod IP from EndpointSlices. The ALB target then also fails its health check.

Startup probe
Idea

The startup probe asks: "Have you finished the boot?" Liveness and readiness wait until it passes.

Example

A Java service needs 90 seconds to start. The startup probe allows 30 x 5 seconds, so liveness does not kill it.

Term

startupProbe with failureThreshold x periodSeconds = the maximum boot time. Use it instead of a long initialDelaySeconds.

Probe settings
Idea

Each probe has numbers that set how often it runs and how many failures it accepts.

Example

periodSeconds: 10, failureThreshold: 3 gives about 30 seconds before action.

Term

The fields are initialDelaySeconds, periodSeconds, timeoutSeconds (default 1s), successThreshold and failureThreshold.

8. Resources: requests, limits and QoS

Requests
Idea

A request is the amount of CPU and memory that the pod reserves. The scheduler uses it to find a node.

Example

A pod requests 500m CPU and 1Gi memory. The scheduler only picks a node with that much free.

Term

Requests drive scheduling and HPA percentages. 1000m = 1 CPU core. Mi and Gi are binary units.

Limits
Idea

A limit is the maximum amount that the container can use at runtime.

Example

A browser container has a 2Gi memory limit. At 2.1Gi it is killed.

Term

Limits are enforced by cgroups on the node. If you set limits and no requests, the request is set equal to the limit.

CPU throttling
Idea

Too much CPU use makes the container slow. Kubernetes does not kill it for CPU.

Example

Tests time out because the browser container is throttled at its 1 CPU limit.

Term

CPU is compressible. The CFS quota throttles the container. Look at container_cpu_cfs_throttled_seconds_total in Prometheus.

Memory OOMKill
Idea

Too much memory use kills the container. Memory cannot be slowed down like CPU.

Example

A test runner leaks memory and is killed after 20 minutes.

Term

Memory is incompressible. Above the limit, the kernel OOM killer sends SIGKILL (exit code 137).

QoS classes
Idea

Kubernetes gives each pod a priority class for eviction, based on its requests and limits.

Example

Under memory pressure, the kubelet evicts BestEffort pods first and Guaranteed pods last.

Term

Guaranteed: requests = limits for CPU and memory in all containers. Burstable: some requests set. BestEffort: no requests and no limits.

9. Config, isolation and permissions

Namespace
Idea

A namespace is a folder inside the cluster. It separates teams and apps.

Example

Team A uses team-a-tests. Team B uses team-b-tests.

Term

Names must be unique only inside a namespace. ResourceQuota, LimitRange, RBAC and NetworkPolicy work per namespace.

ConfigMap
Idea

A ConfigMap holds plain settings outside the image. You change settings without a new build.

Example

BASE_URL=https://staging.example.com lives in a ConfigMap.

Term

Pods read a ConfigMap as env vars (envFrom, configMapKeyRef) or as files. Env vars do not update in a running pod. You must restart the pod.

Secret
Idea

A Secret holds sensitive values such as passwords and tokens.

Example

The DB password for the results service is in a Secret.

Term

Secret data is base64-encoded, not encrypted by default. On EKS, turn on envelope encryption with KMS and limit read access with RBAC. Many teams sync from AWS Secrets Manager.

ServiceAccount
Idea

A ServiceAccount is the identity of a pod. It is like a user account for software.

Example

The pod runs as ServiceAccount results-api. RBAC and AWS permissions attach to that name.

Term

Each namespace has a default ServiceAccount. Set serviceAccountName in the pod spec. Its token is mounted in the pod.

Role and ClusterRole
Idea

A Role is a list of allowed actions inside one namespace. A ClusterRole is the same list for the whole cluster.

Example

A Role allows get, list and create on jobs in team-a-tests.

Term

RBAC rules are apiGroups, resources and verbs. RBAC only allows. It has no deny rules.

RoleBinding and ClusterRoleBinding
Idea

A binding gives a Role to a user, a group or a ServiceAccount.

Example

A RoleBinding gives the Role to the ServiceAccount of the CI runner. Now CI can create Jobs in that namespace.

Term

A RoleBinding can also point to a ClusterRole to reuse it in one namespace. Test it with kubectl auth can-i create jobs --as=system:serviceaccount:ns:sa.

IRSA (IAM Roles for Service Accounts)
Idea

IRSA lets one pod use one AWS IAM role, without keys in the image.

Example

The results pod writes to S3. Other pods on the same node cannot.

Term

Annotate the ServiceAccount with eks.amazonaws.com/role-arn. The pod gets a projected web identity token. The AWS SDK calls AssumeRoleWithWebIdentity. The role trust policy names the cluster OIDC provider and the ServiceAccount.

EKS Pod Identity
Idea

Pod Identity is the newer and simpler way to give a pod an IAM role.

Example

You make one association: cluster + namespace + ServiceAccount → IAM role. No annotation is needed.

Term

It needs the eks-pod-identity-agent add-on. The trust policy principal is pods.eks.amazonaws.com. One role can be reused across clusters. IRSA and Pod Identity are both valid.

Node instance role
Idea

The node instance role is the IAM role of the EC2 node. Every pod on the node can reach it if you do not block it.

Example

If you put S3 write on the node role, every test pod on the node can write to S3.

Term

Use the node role only for node needs (ECR pull, CNI). Give app permissions with IRSA or Pod Identity. Block the instance metadata service for pods where possible.

10. Scaling: more pods and more nodes

HPA (Horizontal Pod Autoscaler)
Idea

The HPA adds or removes pods based on a metric.

Example

At 70% CPU, the HPA increases the results API from 3 pods to 8 pods.

Term

autoscaling/v2 supports CPU, memory, custom and external metrics. It needs metrics-server for CPU and memory. Utilization is a percentage of the request.

KEDA
Idea

KEDA scales pods on events, such as the length of a queue.

Example

200 test sessions wait in a queue. KEDA scales browser pods up, then down to zero overnight.

Term

KEDA (Kubernetes Event-Driven Autoscaling) uses scalers for SQS, Kafka, Prometheus and Selenium Grid. It can scale to zero and can create Jobs.

Cluster Autoscaler
Idea

The Cluster Autoscaler adds nodes when pods cannot fit. It removes empty nodes later.

Example

10 pods are Pending. The Cluster Autoscaler raises the node group from 5 to 8 nodes.

Term

It works through Auto Scaling groups (node groups). It is slower and less flexible than Karpenter, but it is common and simple.

Karpenter
Idea

Karpenter looks at Pending pods and starts the best EC2 instance for them.

Example

Browser pods need 4 CPU and 8Gi each. Karpenter picks a cheap Spot c6i.4xlarge that fits 3 of them.

Term

11. How one request reaches a pod on EKS

flowchart LR
  U["Client"] --> D["Route 53 DNS"]
  D --> A["ALB listener :443 (TLS)"]
  A --> R{"Listener rule: host + path"}
  R --> T["Target group: pod IPs"]
  T --> P["Pod 10.0.12.45"]
  P --> C["Container :8080"]
  L["AWS Load Balancer Controller"] -. "creates from Ingress" .-> A
  L -. "registers ready pods" .-> T
  1. A test or a user calls https://results.test-platform.example.com/runs.
  2. DNS (Route 53) returns the address of the ALB. ExternalDNS can create this record from the Ingress host.
  3. The ALB listener gets the request on port 443 and ends TLS with an ACM certificate.
  4. The ALB checks its listener rules. The host and path match, so the rule forwards to one target group.
  5. The AWS Load Balancer Controller made this ALB, rule and target group from the Ingress object.
  6. With target type ip, the target group holds pod IPs, for example 10.0.12.45:8080. The controller updates the list when pods change.
  7. The ALB sends the request only to targets that pass the target group health check.
  8. The packet goes straight to the pod. This works because the VPC CNI gives each pod a real VPC IP address.
  9. The packet arrives at the container port (targetPort 8080). The app handles it and sends the response back the same way.
  10. With target type instance, there is one more hop: the ALB sends to a NodePort on a node, and kube-proxy forwards to a pod.
  11. Inside the cluster, pod-to-pod calls do not use the ALB. A pod calls the Service name, CoreDNS gives the ClusterIP, and kube-proxy picks a ready pod.

GitHub Actions

GitHub Actions runs workflows when events happen in a repo. A workflow has jobs, and each job runs on a runner and has steps. On this team, your job is to make CI a shared, safe and fast product for hundreds of teams.

UKG-G1

One CI for 300 repos

Interviewer

We have about 300 repos. Every team copy-pasted its own E2E workflow, so we have 300 slightly different YAML files. A security fix takes months to reach everyone. How would you centralize this?

What this tests The interviewer tests if you can design CI as a shared product with versions, ownership and a rollout plan.

Say this (30 seconds), then stop

I move the common E2E logic into one reusable workflow that the platform team owns. Each repo keeps a short caller file that uses workflow_call with a version tag. I pin every third-party action to a commit SHA, and an org ruleset makes the shared check required. I roll out in waves with automated pull requests and give the old YAML a clear end date. After that, a security fix is one release, not 300 pull requests.

Full Staff-level answer

  1. 1. Find out what exists

    Inventory the 300 workflows first. Use the GitHub code search API or a script to group them by shape. Usually 4 or 5 patterns cover more than 80% of the repos. Note the real differences, such as the Node version, the test command and the browsers.

  2. 2. Build the shared layer

    Use two building blocks:

    • A reusable workflow (on: workflow_call) for whole jobs: checkout, setup, shard, test, report.
    • Composite actions for small step groups that teams mix into their own jobs, for example "setup test env".

    Put both in one repo, for example ukg/test-platform-workflows. Expose only the real differences as inputs.

  3. 3. Version it like a product

    Release with SemVer tags such as v3.2.0 and a moving major tag v3. Teams call @v3 to get fixes, or a commit SHA when they need full immutability. Inside the shared workflow, pin all third-party actions to a full commit SHA. Use Dependabot or Renovate to raise the SHA pins.

  4. 4. Enforce the minimum with rulesets

    Use organization rulesets to require the shared workflow to pass before merge on protected branches. This sets the floor for every repo. It does not force every team to use the same detail.

  5. 5. Roll out and deprecate

    Start with 3 to 5 friendly pilot repos. Then open automated pull requests that replace the old YAML with the caller file. Add a warning annotation to the old patterns and publish a removal date. Track adoption on a dashboard: repos on the shared workflow, and which version.

  6. 6. Make ownership clear

    The platform team owns the shared workflow, with CODEOWNERS, a changelog and an on-call rotation. Teams can contribute through pull requests and an RFC for big changes. Provide a template repo so new services start on the shared workflow from day one.

Concepts you must own 11

Reusable workflow
Idea

A reusable workflow is a whole workflow that other workflows call, like a function.

Example

Team A writes 8 lines that call ukg/test-platform-workflows/.github/workflows/e2e.yml@v3. All jobs come from the shared file.

Term

The called file has on: workflow_call with inputs, secrets and outputs. The caller uses jobs.<id>.uses: owner/repo/.github/workflows/file.yml@ref. Nesting depth is limited.

workflow_call inputs
Idea

Inputs are the parameters that a caller gives to the reusable workflow.

Example

with: { node-version: "20", test-command: "npm run e2e" }.

Term

Inputs have a type (string, number, boolean), an optional default and required. Read them as ${{ inputs.name }}.

secrets: inherit
Idea

secrets: inherit passes all the caller's secrets to the reusable workflow, so you do not list each one.

Example

The caller has TEST_USER_PASSWORD. The shared workflow can read it without an explicit mapping.

Term

It works only when the caller and the called workflow are in the same organization or enterprise. Explicit secrets: mapping is safer because it shows exactly what passes.

Composite action
Idea

A composite action is a group of steps packed as one step.

Example

uses: ukg/actions/setup-test-env@v2 installs Node, restores caches and installs browsers in one line.

Term

It has runs: using: composite in action.yml. It runs inside the caller job, so it cannot set runs-on or own jobs. It cannot read secrets directly; pass them as inputs.

Reusable workflow vs composite action
Idea

Use a reusable workflow to share whole jobs. Use a composite action to share a few steps inside a team's own job.

Example

The full E2E pipeline is a reusable workflow. "Upload results to the results service" is a composite action.

Term

Reusable workflows control runners, matrices, environments and permissions. Composite actions are more flexible but give less control and less visibility in the UI.

Versioning by tag or SHA
Idea

A version reference decides which copy of the shared workflow a repo runs.

Example

@v3 follows the newest v3 release. @v3.2.1 is fixed. @9f3e... is fixed and cannot move.

Term

Tags can be moved or deleted, so a commit SHA is the only immutable reference. Many platforms use a major tag for speed and a SHA for high-risk repos.

Organization rulesets and required workflows
Idea

A ruleset is an org-wide rule. It can make a workflow a required check before merge in many repos at one time.

Example

The ruleset says: on main in all repos with property tier=prod, the e2e workflow must pass.

Term

Organization rulesets target repos by name or custom property. The "require workflows to pass before merging" rule replaced the older "required workflows" feature.

Template repository
Idea

A template repo is a starter repo. New repos copy it, including the workflow caller file.

Example

A new service made from ukg/service-template has CI on day one.

Term

Mark a repo as a template in its settings. A copy does not follow later changes, so keep the logic in the reusable workflow, not in the template.

Pin third-party actions to a commit SHA
Idea

A tag on a third-party action can change. If an attacker changes it, your CI runs their code with your secrets.

Example

In March 2025, the tj-actions/changed-files tags were moved to malicious code. Repos pinned to a SHA were safe.

Term

Use uses: owner/action@<40-char-sha> # vX.Y.Z. Use Dependabot or Renovate to update the pins. An org policy can allow only listed actions.

Rollout and deprecation of old YAML
Idea

Move teams in waves and give the old way an end date. Do not switch all 300 repos in one day.

Example

Wave 1: 5 pilot repos. Wave 2: automated pull requests to 100 repos. Wave 3: the rest, with help.

Term

Use automated pull requests (a script or Renovate), warning annotations (::warning::) in the old pattern, an adoption dashboard and a published removal date.

Ownership of the shared workflow
Idea

One team must own the shared workflow, or it will rot.

Example

The test platform team owns it, reviews changes and answers incidents when it breaks CI for many teams.

Term

Use CODEOWNERS, a changelog, SemVer releases, an RFC for breaking changes and a support channel. Contributors outside the team can still send pull requests.

Code to know

Follow-up questions

  • A team needs a step that the shared workflow does not have. What do you do?

    Add an extension point, such as an optional pre-test-command input or a separate job that runs before or after the reusable workflow. If many teams need it, put it in the shared workflow. I do not want teams to fork the shared file.

  • How do you ship a fix to all teams fast, for example a security fix?

    Release a PATCH version and move the v3 tag, so every @v3 caller gets it on the next run. Repos that pin a SHA get an automated pull request from Renovate. For a severe issue, I also announce it and track which repos still run the old version.

  • Why not use only composite actions?

    Composite actions cannot own the runner, the matrix, the environment or the job permissions. So each repo still writes most of the job, and drift comes back. Composite actions are good building blocks inside the reusable workflow.

  • How do you test a change to the shared workflow before release?

    The shared repo has its own CI that calls the workflow against a few sample repos. Then I release an RC tag and ask canary teams to point at it for a few days. Only then do I move the major tag.

Caution
  • Some candidates say "put the YAML in a template repo". A template is a one-time copy, so drift starts again on day two.
  • Some candidates pin shared actions to @main. Then any merge changes 300 pipelines with no version and no rollback.
  • Some candidates use secrets: inherit everywhere without thought. It passes every secret, so a bug in the shared workflow can expose all of them.
  • Some candidates force the change on all repos in one day. This breaks many teams and destroys trust in the platform.
Staff signal

A Staff answer treats the shared workflow as a product. It has an owner, versions, a contribution path, an adoption metric and a deprecation plan, not only a YAML file.

45 minutes to 10 minutes

Interviewer

The E2E pipeline for a large monorepo takes 45 minutes and developers bypass it. Get it under 10 minutes without losing coverage.

What this tests The interviewer tests if you measure first and then use parallelism, caching and test selection with clear trade-offs.

Say this (30 seconds), then stop

First I measure the time of each job and step, because I need to know where the 45 minutes go. Then I fix the biggest costs: caches for dependencies and browsers, sharding with a matrix, and path filters so a PR runs only affected tests. I add tiers: a fast smoke set on each PR, the full set on merge, and the long set nightly. Coverage stays the same because every test still runs at some tier.

Full Staff-level answer

  1. 1. Measure before you change anything

    Get the time of each job and step from the run logs or the GitHub API. Split the 45 minutes into queue time, setup time and test time. Also find the 20 slowest test files. A small number of files usually take most of the time.

  2. 2. Remove waste in setup
    • Cache dependencies with actions/setup-node cache: npm or actions/cache keyed on the lockfile hash.
    • Cache browser binaries and build outputs.
    • Build the app one time, upload it as an artifact, and download it in each test job.

    This often saves 5 to 10 minutes per job.

  3. 3. Run tests in parallel

    Use a strategy.matrix to split the suite into shards, for example 8 shards with --shard=i/8. Use the needs graph: one build job fans out to many test jobs, then one report job fans in. Balance shards by test duration, not by file count.

  4. 4. Run only what the change affects

    Use paths triggers or dorny/paths-filter so a change in apps/billing does not run the apps/hr suite. In a monorepo, a tool such as Nx or Turborepo can compute the affected projects. Always run a small smoke set, so a bad filter cannot hide a total break.

  5. 5. Add test tiers
    • PR: smoke tests plus affected tests, target under 10 minutes.
    • Merge to main: the full suite, sharded.
    • Nightly: slow, cross-browser and long-running tests.

    Every test still runs at some tier, so coverage is the same. Only the time of feedback changes.

  6. 6. Stop waste and decide on runners

    Add a concurrency group with cancel-in-progress: true so a new push cancels the old run on that PR. Use larger runners for CPU-heavy jobs if the cost is lower than the developer time saved. Choose fail-fast on purpose: off for full reports, on for quick PR feedback.

  7. 7. Protect the result

    Put the pipeline time on a dashboard with a budget, for example p90 under 10 minutes. Alert when the trend goes up. Without this, the time grows back in six months.

Measure per job and per step
Idea

You cannot fix time that you have not measured.

Example

The data shows 12 minutes for npm ci and browser install in every shard. Test time is only 20 minutes.

Term

Get timings from the Actions UI, the REST API (/actions/runs/{id}/jobs has step start and end times) or OpenTelemetry export. Separate queue time from run time.

Sharding with a matrix
Idea

Split the tests into equal parts and run the parts at the same time on different runners.

Example

8 shards of 4 minutes each instead of one run of 32 minutes.

Term

strategy.matrix.shard: [1..N] with npx playwright test --shard=${{ matrix.shard }}/${{ strategy.job-total }}. Each matrix entry is a separate job. The maximum is 256 jobs per matrix.

Test impact and path filters
Idea

Run only the tests for the code that changed.

Example

A PR changes only apps/web/**. The API contract tests do not run.

Term

Use on.pull_request.paths to skip whole workflows. Use dorny/paths-filter to skip single jobs, because it gives outputs that if: can read. Nx and Turborepo compute affected projects from the dependency graph.

Caching with actions/cache
Idea

A cache saves files from one run and gives them back in the next run, so you do not download them again.

Example

~/.cache/ms-playwright is restored, so browsers are not downloaded again.

Term

key is an exact match, for example a hash of package-lock.json. restore-keys are prefix fallbacks for a partial hit. Caches are scoped by branch, and a PR can read the cache of the base branch.

Dependency cache vs build cache
Idea

A dependency cache keeps downloaded packages. A build cache keeps compiled output.

Example

Dependency cache: ~/.npm. Build cache: .next/cache or the Nx cache.

Term

Key the dependency cache on the lockfile. Key the build cache on source hashes. A wrong key gives stale builds, so include every input that changes the output.

Artifacts between jobs
Idea

An artifact is a file that one job uploads and another job downloads.

Example

The build job uploads dist/. Eight test jobs download it and do not build again.

Term

actions/upload-artifact@v4 and actions/download-artifact@v4. Artifacts are for passing results and reports. Caches are for speed. In v4, artifact names must be unique in a run.

Idea

needs sets the order of jobs. One job can start many jobs, and many jobs can feed one job.

Example

Term

Jobs without needs run in parallel. needs can read outputs (needs.build.outputs.x). Use if: ${{ !cancelled() }} on the fan-in job so it runs after failures too.

Concurrency groups with cancel-in-progress
Idea

A concurrency group lets only one run per group continue. A new run can cancel the old one.

Example

A developer pushes 3 commits in 2 minutes. Only the last commit runs to the end.

Term

concurrency: { group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true }. Do not cancel runs on main deploys, or you can lose a deploy.

Larger runners
Idea

Larger runners are GitHub-hosted machines with more CPU and memory.

Example

A 16-core runner runs 4 Playwright workers per shard instead of 2.

Term

They are set up at org level with a label and cost more per minute. Compare cost per run and developer wait time. Self-hosted runners are the other option.

Test tiering
Idea

Run fast, important tests often and slow tests less often.

Example

PR: 150 smoke tests. Merge: 2,000 tests. Nightly: 6,000 tests on 3 browsers.

Term

Use tags (@smoke, @regression) with --grep. Each tier has an owner and a time budget. A failed nightly test must create a ticket, or the tier has no value.

fail-fast trade-offs
Idea

With fail-fast on, the first failed shard cancels the other shards.

Example

On a PR, a failure in shard 2 stops shards 3 to 8 and gives fast feedback.

Term

Follow-up questions

  • Shards are unequal. One shard takes 9 minutes and the others take 3. What do you do?

    Split by test duration, not by file count. Store the timing of each file from earlier runs and give each shard an equal total. Also split very large spec files, because one file cannot cross shards in many tools.

  • How do you make sure path filters do not hide a real break?

    Always run a small smoke set on every PR. Run the full suite on merge to main and nightly. Also review the filter map when shared packages change, because a shared package affects everything.

  • Does more shards always help?

    No. Each shard pays a fixed setup cost, so after some point extra shards only add cost and queue time. Find the point where setup time is a small part of each shard.

  • Some candidates use caches with keys that ignore some inputs. Stale caches give wrong results that are very hard to debug.
  • Some candidates turn on retries to make the suite green faster. That hides flaky tests and does not save time.

A secret leaked from a fork PR

Interviewer

A test log printed a production API key. The run came from a pull request built off a fork. Contain it, and redesign so this cannot happen again.

What this tests The interviewer tests if you act in the right order in an incident and know the GitHub Actions trust model.

Say this (30 seconds), then stop

First I rotate the key, because a key in a log is already compromised. Then I check the audit logs and the provider logs for use of the key, and I delete the logs that contain it. The likely root cause is pull_request_target or a self-hosted runner that gave secrets to fork code. For the redesign I use OIDC to AWS instead of long-lived keys, and I put prod secrets behind an environment with required reviewers. I also set least-privilege permissions: and turn on secret scanning with push protection.

Full Staff-level answer

  1. 1. Contain now
    • Revoke and rotate the key immediately. Do not wait for the investigation.
    • Delete the workflow run logs that show the key.
    • Disable the workflow or block fork runs until the fix is in.
    • Tell security, because a production key is an incident.
  2. 2. Find out the impact

    Check the provider logs for use of the key from unknown IPs. Check the GitHub audit log for who triggered the run and who viewed or downloaded logs and artifacts. Check whether the PR changed the workflow or the test code that printed the key.

  3. 3. Find the root cause

    Fork PRs do not get secrets with the pull_request trigger. So something gave them access:

    • pull_request_target that checks out the fork code and runs it with secrets.
    • An org setting that sends secrets to fork PRs.
    • A test that printed an encoded or derived value that masking did not catch.
  4. 4. Remove long-lived secrets

    Use GitHub OIDC to AWS. The job asks for a short-lived token, and AWS STS gives temporary credentials. The IAM trust policy accepts only one repo and one environment, for example repo:ukg/app:environment:prod. Then no long-lived AWS key exists to leak.

  5. 5. Put a human gate in front of prod

    Store prod secrets only in a prod environment with required reviewers and branch restrictions. Tests that run on PRs use test credentials with no prod access. Set permissions: to the minimum, for example contents: read, as the org default.

  6. 6. Detect and prevent

    Turn on secret scanning and push protection for the org. Add a log lint that fails a job if it prints known secret patterns. Write a short postmortem and a rule for pull_request_target: it must never check out and run PR code.

Rotate first
Idea

A secret that appeared in a log is compromised. Replace it before you investigate.

Example

You revoke the old API key and issue a new one. Then you look at who used the old key.

Term

Incident order: contain (revoke, rotate), then assess (logs), then fix the root cause, then prevent. Deleting the log alone does not help, because someone can have copied it.

pull_request vs pull_request_target
Idea

pull_request runs the PR code with no secrets for forks. pull_request_target runs in the context of the base repo, with secrets.

Example

A workflow on pull_request_target checks out github.event.pull_request.head.sha and runs npm test. The fork's test code can now read secrets.

Term

pull_request_target uses the workflow from the base branch and gets a write token and secrets. It is safe only when it does not run untrusted code, for example for labeling. This danger is called a "pwn request".

Fork PRs get no secrets by default
Idea

GitHub does not give secrets to workflows that run from a fork PR.

A contributor opens a PR from a fork. ${{ secrets.API_KEY }} is empty.

Term

With pull_request from a fork, secrets are not passed (except GITHUB_TOKEN, which is read-only). Org settings can change this for private repos, so check them.

Idea

GitHub hides registered secret values in logs with ***. It cannot hide every changed form of a secret.

The test prints the key in base64, or prints only part of it. The log shows the real value.

A job with environment: prod waits until a person from the release group approves it.

Term

Each job gets an automatic GITHUB_TOKEN. Give it only the rights that the job needs.

A test job needs contents: read only. It cannot push code or change releases.

The deploy job gets 1-hour credentials for gha-results-deploy. No AWS key is stored in GitHub.

Follow-up questions

  • When is pull_request_target safe to use?

    It is safe when the workflow does not run code from the PR. Examples are adding labels or posting a comment. If you must test fork code with secrets, use a two-step design: run tests without secrets, then a trusted workflow_run job that only reads artifacts.

Interviewer

What this tests The interviewer tests if you know the network options, the runner model and the security and cost trade-offs.

Say this (30 seconds), then stop

Full Staff-level answer

  1. 1. Name the problem

    GitHub-hosted runners run on the internet. They have no path to private subnets. So the tests must run inside the VPC, or a network path must come to the runner.

  2. 2. Compare the options
    • Self-hosted runners in the VPC (EC2 VMs or ARC on EKS). This is the usual answer.
    • A VPN or bastion from hosted runners. This is fragile and opens the network.
    • Run the tests inside the cluster as a Kubernetes Job. CI only starts the Job and reads results.
    • Expose a private endpoint with strict IP rules. This increases the attack surface.
    • GitHub Azure private networking exists, but it does not apply to an AWS VPC.
  3. 3. Choose ARC with runner scale sets

    Install Actions Runner Controller on EKS. Create one runner scale set per purpose, for example e2e-private. ARC watches the job queue and creates a runner pod for each job. Workflows use runs-on: e2e-private.

  4. 4. Make runners ephemeral

    Each runner pod runs one job and is then deleted. This stops state bleed, such as left-over files, caches or logged-in sessions. It also limits damage if a job is compromised.

  5. 5. Control access

    Put runner scale sets in runner groups that only some repos can use. Give the runner pods AWS access with IRSA or Pod Identity, or with OIDC from the workflow. Never let public or fork PRs use runners inside the VPC.

  6. 6. Control cost and blast radius

    Set minRunners: 0 and a maxRunners limit. Put runner pods on their own node pool, with Spot nodes for test work. Use a separate namespace with quotas and NetworkPolicies. Runners must reach the test environment, not prod.

UKG-G6

Promote, do not rebuild

Interviewer

Our release pipeline rebuilds the image for staging and again for prod. A prod bug did not reproduce in staging. What is wrong and how do you fix it?

What this tests The interviewer tests if you know immutable artifacts, environment promotion and safe deploy and rollback.

Say this (30 seconds), then stop

A rebuild for each environment makes a different artifact, so staging tests do not prove anything about prod. I build the image one time, tag it with the commit SHA, and promote the same digest to staging and then prod. Prod uses a GitHub environment with required reviewers. Rollback is a redeploy of the previous digest. For many services I prefer GitOps with Argo CD, where CI only changes the image digest in a Git repo.

Full Staff-level answer

  1. 1. Explain the cause

    Each rebuild can pull a different base image, a different dependency version or a different build flag. So the prod image is not the image that staging tested. The bug lived in the difference.

  2. 2. Build once

    Build the image one time on merge to main. Tag it with the commit SHA. Push it to ECR and record the digest (sha256:...). Turn on tag immutability in ECR.

  3. 3. Promote the same digest

    Staging and prod deploy results-api@sha256:..., not a tag. Environment differences come only from config, such as ConfigMaps and secrets, not from the image.

  4. 4. Gate prod

    The prod deploy job uses environment: prod with required reviewers. The gate also needs green staging tests on the same digest.

  5. 5. Deploy with a safe strategy

    Use a rolling update for most services. Use blue/green or canary for high-risk services, with automatic checks on error rate and latency. Argo Rollouts or the load balancer weights can control a canary.

  6. 6. Roll back fast

    Rollback is a redeploy of the previous known-good digest. It needs no rebuild. With GitOps, rollback is a revert of one commit in the config repo.

Interviewer

Pods show Running, the nodes are healthy, but users get a 503 from the ALB. Debug it.

What this tests The interviewer tests if you know the request path and debug it layer by layer, not by guess.

Say this (30 seconds), then stop

Running does not mean Ready, so I check the READY column first. Then I check if the Service has endpoints. An empty EndpointSlice means no pod passes readiness, or the selector does not match the pod labels. If endpoints exist, I check the ALB target group health and compare its health check path and port with the readiness probe. I also find out who returns the 503: the ALB, the ingress controller, or the app.

Full Staff-level answer

  1. 1. Find who returns the 503

    Look at the response headers and body. An ALB 503 has an AWS page and no app headers. An app 503 has the app's own headers and body. The ALB access logs show elb_status_code and target_status_code separately.

  2. 2. Check Running vs Ready

    kubectl get pods shows 0/1 Running when the readiness probe fails. kubectl describe pod shows Readiness probe failed in Events. A failed readiness probe removes the pod from the Service endpoints.

  3. 3. Check the Service endpoints

    Run kubectl get endpointslices -l kubernetes.io/service-name=<svc>. If the list is empty but pods are Ready, compare the Service selector with the pod labels. One typo, such as app: result-api, breaks the link with no error.

  4. 4. Check the ports

    The Service targetPort must be the port that the container listens on. The Ingress backend must use the Service port. Use kubectl port-forward svc/<svc> and curl to test the Service without the ALB.

  5. 5. Check the ALB target group

    Run aws elbv2 describe-target-health. Targets can be unhealthy even when the pods are Ready. A common cause is a health check path such as / that returns 404 or a redirect. Set alb.ingress.kubernetes.io/healthcheck-path to the same path as the readiness probe.

  6. 6. Check the dependencies of the app

    The readiness endpoint can fail because a database or downstream API is down. Then all pods drop out together and the ALB returns 503. Readiness can check critical local state, but a shared outage then removes every pod at one time.

An empty endpoint list means the Service has nowhere to send traffic.

Term

Two causes: no matching pod is Ready, or the selector matches no pod. Both give a 503 at the ingress layer.

Idea

The ALB has its own health check. It can disagree with the Kubernetes probe.

The readiness probe uses /ready on 8080. The ALB checks / and gets a 302 redirect, so it marks targets unhealthy.

Set alb.ingress.kubernetes.io/healthcheck-path, healthcheck-port and success-codes. With target type ip, the health check goes straight to the pod.

The Service finds pods by label. A different label means the Service finds no pod.

The Service selects app: results-api. The new Deployment template has app: results-api-v2.

Wrong targetPort
Idea

The Service sends traffic to a port where nothing listens.

The app moved from 8080 to 3000. The Service still has targetPort: 8080.

App failing a dependency check

The app says "not ready" because something it needs is down.

The test-results DB is in maintenance. Every pod fails /ready. All targets go unhealthy.

Term

Deep readiness checks give cascading failures. Check only what the pod needs to serve. Use timeouts and circuit breakers for dependencies. Never put dependency checks in liveness.

Who returns the 503
Idea

Different layers return a 503 for different reasons. Find the layer first.

Example

ALB 503: no healthy targets. ingress-nginx 503: no endpoints. App 503: the app is overloaded.

Term

Follow-up questions

  • Endpoints exist and targets are healthy, but users still get some 503s. What next?

    Look at timing. A 503 during deploys points to a shutdown race between the ALB and the pod. A 503 under load points to app overload or too few pods. Compare the 503 times with deploys and traffic.

  • Should the readiness probe check the database?

    Only if the pod truly cannot serve any request without it. If all pods check the same database, one database issue removes every pod. Often it is better to stay Ready and return a clear error for that request.

  • What is the difference between a 502, 503 and 504 from an ALB?

    502 means the target sent a bad response or closed the connection. 503 means no healthy target is registered. 504 means the target did not answer in the idle timeout.

CrashLoopBackOff after a config change

Interviewer

A team made a "harmless" config change and now the pods are in CrashLoopBackOff. Walk me through it.

What this tests The interviewer tests if you can read pod evidence fast, restore service, and fix the process.

Say this (30 seconds), then stop

First I restore service with kubectl rollout undo or a revert of the config in Git. Then I read kubectl logs --previous for the crash message and kubectl describe pod for the exit code and events. Common causes are a missing env var or Secret key, a liveness probe that kills a slow start, or OOMKilled with exit code 137. The process fix is that config changes go through the same pipeline and review as code.

Full Staff-level answer

  1. 1. Restore service first

    If the change was in the Deployment, run kubectl rollout undo. If the change was only in a ConfigMap, revert it and run kubectl rollout restart. A ConfigMap change does not make a new ReplicaSet, so rollout undo cannot revert it.

  2. 2. Read the crashed container's log

    Use kubectl logs <pod> --previous. The current container has just started and has no useful log. Look for errors such as "missing env var" or "cannot parse config".

  3. 3. Read the pod details

    Use kubectl describe pod. Look at Last State, Reason and Exit Code, and the Events at the bottom.

    • OOMKilled, exit code 137: memory limit.
    • Exit code 1: app error.
    • Liveness probe failed events: probe killed the app.
    • CreateContainerConfigError: missing ConfigMap, Secret or key.
  4. 4. Check the probes

    A config change can make start-up slower, for example a bigger cache. A liveness probe with a short delay then kills the app again and again. Add a startup probe that allows the full boot time.

  5. 5. Check the image

    Confirm that the running image tag is the one that the change expected. A config that needs a newer app version fails on an older image.

  6. 6. Fix the process

    Config lives in Git and goes through review and CI, like code. Validate it with a schema check before deploy. Add a hash of the config to the pod annotations, so a config change makes a normal, reversible rollout.

2,000 browser sessions at 9 AM

Interviewer

Teams need 2,000 parallel browser sessions at 9 AM and almost none overnight. Design Selenium Grid or Playwright workers on EKS for this.

What this tests The interviewer tests if you can design elastic, isolated and cost-aware infrastructure for a bursty workload.

Say this (30 seconds), then stop

I run each browser as a pod, and I scale on the length of the test queue with KEDA, not on CPU. Karpenter adds Spot nodes in a dedicated, tainted node pool, so browsers never starve app workloads. Each browser pod has a fixed request and limit and a memory-backed /dev/shm. Sessions have a hard timeout and Jobs clean up after themselves. I tag everything by team, so we can show cost per team.

Full Staff-level answer

  1. 1. Choose the unit of work
    • Selenium Grid 4: a hub (router, distributor, session queue) and browser node pods. Good for existing Selenium suites.
    • Playwright: each worker is a Kubernetes Job that runs one shard and exits. No grid is needed.

    Either way, one browser session is one isolated pod, or one container with a fixed number of sessions.

  2. 2. Size the browser pods

    A Chrome session needs about 1 CPU and 1 to 2 GiB of memory. Measure it on your real tests. Set the memory limit equal to the request, so the scheduler never overcommits memory. Mount an emptyDir with medium: Memory at /dev/shm. The 64Mi default crashes Chrome tabs.

  3. 3. Scale pods on the queue

    CPU is a bad signal, because an idle browser uses little CPU while tests wait. KEDA reads the Selenium Grid session queue or an SQS queue of shards. It scales browser pods or Jobs from zero to the needed number.

  4. 4. Scale nodes fast and cheap

    Karpenter sees Pending browser pods and starts right-sized nodes in about a minute. Use Spot instances for most of the capacity, with On-Demand as a fallback. Consolidation removes idle nodes after the peak.

  5. 5. Handle Spot interruptions

    Karpenter drains a node on the 2-minute interruption notice. Each test shard must be retryable, so a lost node only re-runs a few shards. Record these re-runs as infra retries, not as test failures.

  6. 6. Isolate the browser pool

    Put a taint workload=browsers:NoSchedule on the browser nodes and a matching toleration on browser pods. Use a separate namespace with a ResourceQuota per team. Then 2,000 browsers cannot evict the results API or other apps.

  7. 7. Clean up and control cost

    Set activeDeadlineSeconds and session timeouts so a stuck browser dies. Set ttlSecondsAfterFinished to delete finished Jobs. Label pods by team and use cost allocation tags or Kubecost to show cost per team.

Interviewer

One team's test job keeps evicting other teams' pods on a shared cluster. Fix it.

What this tests The interviewer tests if you know multi-tenant controls in Kubernetes and can apply them fairly.

Say this (30 seconds), then stop

The usual cause is pods with no requests or very low requests that then use far more memory. The node runs out of memory, and the kubelet evicts pods, with BestEffort and over-request pods first. I give each team a namespace with a ResourceQuota and a LimitRange for default requests and limits. Platform services get a higher PriorityClass and a PodDisruptionBudget. Full Staff-level answer

  1. 1. Confirm the mechanism

    Look at the evicted pods: kubectl get events shows Evicted with The node was low on resource: memory. Compare the requests of the noisy pods with their real use in kubectl top pods. Usually the noisy job requests little and uses a lot.

  2. 2. Set defaults and limits per team

    Give each team its own namespace. A LimitRange sets default requests and limits for containers that set nothing. A ResourceQuota caps the total CPU, memory and pods per namespace.

  3. 3. Make requests honest

    Requests must be close to real use. Then the scheduler does not overpack nodes. Use Guaranteed QoS (requests equal limits) for important services. Use VPA in recommendation mode to suggest values.

  4. 4. Protect critical pods

    Give shared platform services a PriorityClass that is higher than test jobs. Add a PodDisruptionBudget for voluntary disruptions such as node drains.

  5. 5. Separate heavy work

    Put heavy test jobs on a dedicated node pool with taints and tolerations. Then their spikes cannot touch other workloads.

  6. 6. Make cost visible

    Show use and cost per namespace. Chargeback or showback makes teams care about honest requests.

UKG-K5

Zero-downtime deploy that is not

Interviewer

Our rolling update should be zero downtime, but we drop requests for about 30 seconds on every deploy. Why, and how do you fix it?

What this tests The interviewer tests if you understand pod shutdown timing and the race with the load balancer.

Say this (30 seconds), then stop

The pod and the ALB do not agree about time. Kubernetes sends SIGTERM to the pod while the ALB still sends it traffic for some seconds. I add a preStop sleep so the pod keeps serving while it is removed from the target group. The app must handle SIGTERM and drain its open connections. I set maxUnavailable: 0, align the ALB deregistration delay with terminationGracePeriodSeconds, and turn on the ALB pod readiness gate.

Full Staff-level answer

  1. 1. Explain the race

    When a pod stops, two things happen in parallel. The kubelet sends SIGTERM to the container. At the same time, the endpoint is removed, and the controller deregisters the target from the ALB. The ALB change takes several seconds, so the ALB still sends requests to a pod that already shuts down.

  2. 2. Keep the pod alive a little longer

    Add a preStop hook that sleeps for 15 to 20 seconds. The kubelet runs preStop before it sends SIGTERM. During the sleep, the ALB and kube-proxy remove the pod.

  3. 3. Shut down gracefully

    The app must catch SIGTERM, stop new connections, finish open requests and then exit. Set terminationGracePeriodSeconds larger than the preStop sleep plus the drain time. After the grace period, the kubelet sends SIGKILL.

  4. 4. Align the ALB

    Set the ALB deregistration_delay.timeout_seconds to a value that fits inside the grace period, for example 30 seconds. The default of 300 seconds is longer than most grace periods.

  5. 5. Start new pods safely

    Use maxUnavailable: 0 and maxSurge: 1 so capacity never drops. Turn on the AWS Load Balancer Controller pod readiness gate. Then a new pod is Ready only after the ALB marks its target healthy, so the rollout does not move too fast.

  6. 6. Cover node drains

    Add a PodDisruptionBudget, so node upgrades and Karpenter consolidation do not stop too many pods at once. Test the result with a load test during a deploy and count the errors.

maxSurge and maxUnavailable
Idea

These two numbers control how fast a rolling update swaps pods.

Example

maxSurge: 1, maxUnavailable: 0: add one new pod, wait until it is ready, then remove one old pod.

Term

Defaults are 25% each. maxUnavailable: 0 keeps full capacity during the rollout, at the cost of one extra pod.

Readiness gates
Idea

A readiness gate adds an extra condition before a pod counts as Ready.

Example

A new pod is Ready only when its ALB target is healthy, not only when its own probe passes.

Term

The AWS Load Balancer Controller injects the gate when the namespace has the label elbv2.k8s.aws/pod-readiness-gate-inject=enabled. It works with target type ip.

preStop hook
Idea

A preStop hook runs a command inside the container just before Kubernetes asks it to stop.

Term

The kubelet runs preStop first, then sends SIGTERM. The preStop time counts against terminationGracePeriodSeconds. Newer Kubernetes versions also have a built-in sleep action.

terminationGracePeriodSeconds

This is the total time that a pod gets to stop before a forced kill.

With a value of 60: preStop sleeps 20 seconds, the app drains for up to 40 seconds, then SIGKILL.

Term

The ALB keeps a removed target for a while, so open requests can finish. If the pod dies first, those requests fail.

Graceful SIGTERM handling
Idea

The app must react to SIGTERM by finishing its work, not by dying at once.

Example

A Node.js app calls server.close() on SIGTERM. It stops new connections and waits for open requests.

Term

SIGTERM is the polite stop signal. The process must be PID 1 or forward signals. A shell wrapper can swallow the signal, so use exec or an init such as tini.

Idea

Draining means that no new requests go to the pod, but open requests can finish.

A long test-results upload completes before the old pod exits.

Term

Draining happens at the load balancer (deregistration delay) and in the app (graceful shutdown). Keep-alive connections need extra care: send Connection: close during shutdown.

During an EKS node upgrade, minAvailable: 3 lets only one of four pods stop at a time.

  • How do you prove the fix works?

    Run a steady load with a tool such as k6 during a deploy. Count non-2xx responses before and after the fix. Put this check into the platform's deploy pipeline.

    Yes. A Selenium hub or results API that drops requests during a deploy shows up as flaky tests for hundreds of teams.

Node NotReady storm

Interviewer

During a load test, several nodes go NotReady and pods pile up in Pending. What is going on and what do you do?

What this tests The interviewer tests if you can separate node health, scheduling and network capacity problems under pressure.

Say this (30 seconds), then stop

I check the node conditions first: memory pressure, disk pressure, or a kubelet that stopped reporting. Then I read the Pending reasons with kubectl describe pod. They can be insufficient CPU, a taint, or no free IP addresses. On EKS, the VPC CNI gives each pod a real VPC IP, so pods per node and the subnet size can run out. Fixes are prefix delegation, larger subnets, correct requests, and system reserves for the kubelet. I watch all of this in Container Insights or Prometheus.

Full Staff-level answer

  1. 1. Stabilize

    Pause or slow down the load test. Cordon the bad nodes, so no new pods go there. Let the autoscaler add healthy capacity.

  2. 2. Read node conditions

    Use kubectl describe node. Look for MemoryPressure, DiskPressure, PIDPressure and Ready=False. If the kubelet stopped posting status, the node may be out of memory itself, because pods had no limits.

  3. 3. Read Pending reasons

    Use kubectl describe pod on a Pending pod. Typical messages:

    • Insufficient cpu or Insufficient memory: the nodes are full by requests.
    • untolerated taint: no node accepts the pod.
    • failed to assign an IP address: the VPC CNI has no free IPs.
  4. 4. Check IP capacity

    With the VPC CNI, each pod uses one VPC IP. The instance type limits the number of ENIs and IPs, so it limits pods per node. The subnet can also run out of free addresses. Turn on prefix delegation and use larger subnets or secondary CIDRs.

  5. 5. Check the autoscaler

    Read the Karpenter or Cluster Autoscaler logs. It can be at its limit, blocked by a NodePool limit, unable to get Spot capacity, or out of subnet IPs.

  6. 6. Protect the nodes

    Set requests and limits on all pods, so the node is not overcommitted. Keep kube-reserved and system-reserved so the kubelet has room. Add alerts for node conditions, Pending time and free subnet IPs.

Concepts you must own 8

kubelet health
Idea

A node is Ready only while its kubelet reports to the control plane.

Example

The kubelet runs out of memory and stops sending heartbeats. After about 40 seconds the node becomes NotReady.

Term

The kubelet updates a Lease object in kube-node-lease. If updates stop, the node controller marks the node Unknown/NotReady. After a timeout, pods on it are evicted.

Disk and memory pressure
Idea

When a node is low on memory or disk, the kubelet sets a pressure condition and evicts pods.

Example

Browser screenshots and videos fill the node disk. DiskPressure=True, and images are garbage-collected.

Term

Conditions are MemoryPressure, DiskPressure and PIDPressure. They add taints such as node.kubernetes.io/disk-pressure that block new pods.

IP exhaustion with VPC CNI
Idea

Every pod needs a real VPC IP. When the node or subnet has none left, new pods cannot start.

Example

An m5.large supports at most 29 pods with the default VPC CNI mode, whatever its free CPU.

Term

Max pods is based on ENIs per instance and IPs per ENI. Errors appear as failed to assign an IP address to container in pod events and aws-node logs.

Subnet sizing
Idea

The subnet is the pool of IP addresses for nodes and pods. A small subnet fills fast.

Example

A /24 subnet has 251 usable IPs. 2,000 browser pods need far more.

Term

Plan pod subnets large, for example /19 or more per AZ. You can add secondary CIDRs (such as from 100.64.0.0/10) with VPC CNI custom networking.

Prefix delegation
Idea

Prefix delegation gives each ENI slot a block of 16 IPs instead of one IP.

Example

With prefix delegation, an m5.large can run 110 pods instead of 29.

Term

Set ENABLE_PREFIX_DELEGATION=true on the VPC CNI. It needs Nitro instances and free contiguous /28 blocks in the subnet. Set max pods to match.

Pending reasons through kubectl describe
Idea

The scheduler writes why it cannot place a pod.

Example

Term

Main reasons: insufficient resources, taints, node affinity or selector mismatch, an unbound PVC, and no IPs. The message counts nodes per reason.

Autoscaler behavior
Idea

The node autoscaler adds nodes only for pods that could fit on a new node.

Example

Karpenter does not add nodes because the NodePool reached its CPU limit.

Term

Karpenter and Cluster Autoscaler act on unschedulable pods. They cannot fix IP exhaustion in a full subnet. Check their logs, limits and Spot availability.

Observability: Container Insights, Prometheus and Grafana
Idea

You need metrics to see the problem before nodes fail.

Example

A Grafana panel shows node memory at 95% and free subnet IPs at 12 before the storm.

Term

CloudWatch Container Insights gives managed cluster metrics and logs. Prometheus with kube-state-metrics and node-exporter gives detailed metrics for Grafana. Alert on node conditions, Pending pods and IP use.

  • Why did the node go NotReady and not just evict pods?

    If pods have no memory limits, they can use memory faster than the kubelet can evict them. The kubelet itself then starves and stops reporting. System reserves and limits prevent this.

  • How do you plan IP capacity for 2,000 browser pods?

  • How would you run load tests so they do not break the shared cluster?

  • Some candidates look at CPU use only. Pending pods depend on requests, IPs and taints, not live CPU use.

UKG-D1

One API-testing layer, and the framework decision

Interviewer

Design one API-testing layer for REST, SOAP and GraphQL that 100 teams can use. Related, from round one: hundreds of teams use Selenium today. Do we build a custom framework, keep Selenium, or move to Playwright, and how do we support REST, SOAP and GraphQL API testing?

What this tests The interviewer tests if you decide with criteria and design clean extension points, not if you name a favorite tool.

Say this (30 seconds), then stop

I do not start from a tool. I start from criteria: maintenance cost, reliability, speed, hiring, ecosystem, migration cost and time to value. For APIs, I build one client interface with protocol adapters for REST, SOAP and GraphQL, a common response model, and auth plugins. Then assertions are the same for every protocol, and language choice is secondary.

Full Staff-level answer

  1. 1. Correct the round-one answer

    "Selenium, in Java, because it is compatible with everything" answers the wrong question. Compatibility is only one criterion. The real question is which option gives the lowest total cost and the best signal for hundreds of teams over the next few years.

  2. 2. Decide with explicit criteria

    Compare the options on:

    • Reliability: auto-wait and less flakiness.
    • Speed and parallelism, and the cost of infrastructure.
    • Debugging: traces, video and network logs.
    • Maintenance cost for the platform team.
    • Ecosystem, hiring and community.
    • Language fit with the teams.
    • Migration cost and time to value.
  3. 3. Give the recommendation
    • Build a full custom framework: no. It has a high cost, it is hard to hire for, and it re-invents what tools already do.
    • Keep Selenium for everything: no for new work. It needs more custom wait and grid code and gives weaker debugging.
    • Playwright plus a thin UKG layer: yes. It has auto-wait, built-in tracing, sharding, browser contexts and API testing in the same runner.

    Selenium stays supported for existing suites while teams migrate. I validate the choice with a spike on 2 or 3 real team suites.

  4. 4. Design the API layer

    One ApiClient interface that tests use. Behind it, one adapter per protocol:

    • REST adapter: HTTP verbs, JSON, status codes.
    • GraphQL adapter: one endpoint, query and variables, reads the errors array.
    • SOAP adapter: XML envelopes from the WSDL, reads SOAP Faults.

    Config selects the adapter per service, so tests do not contain protocol code.

  5. 5. Normalize the response

    Every adapter returns the same model: status, ok, data, errors, headers and timing. Assertions such as toBeOk() or toRespondWithin(800) then work for every protocol. This is where most of the value comes from.

  6. 6. Add auth plugins and extension points

    Auth is a plugin: OAuth client credentials, API key, mTLS, or a team-specific SSO token. Teams can add their own adapter or auth plugin through a documented interface. They do not need to change the core.

  7. 7. Address language

    Language is secondary. If most teams write TypeScript, Playwright with TypeScript is the natural choice. If many teams are Java, Playwright also has a Java binding, and the same adapter design works in Java. The architecture matters more than the language.

Full Staff-level answer

  1. 1. Separate two kinds of data
    • Reference data: products, tax tables, org structure. Seed it one time and treat it as read-only.
    • Per-test data: the employee, the timesheet, the order that the test changes. Each test creates its own.
  2. 2. Make data unique and traceable

    Give every created record a prefix with the run ID and a short random part, for example e2e-8812-a1b2-emp. Two parallel tests can never pick the same record. A person can see which run created it.

  3. 3. Set up through the API

    Create data through APIs or data factories, not by clicking in the UI. A UI setup takes minutes and fails for reasons that the test does not care about. Test the UI only for the feature under test.

  4. 4. Clean up in layers
    • Teardown in a fixture that runs even when the test fails.
    • Cleanup that is idempotent: a 404 on delete counts as success.
    • A startup sweep that deletes prefixed records older than a few hours.
    • A nightly job as a last safety net.
  5. 5. Isolate more where needed

    Use a tenant or org per team where the product supports it. For risky changes, create an ephemeral environment per PR, for example a namespace per PR on EKS. Weigh the cost: each ephemeral environment uses compute and needs seed data.

    At Joyent, our Cypress tests created real cloud resources such as compute instances. Unique names and cleanup kept tests isolated. A startup cleanup removed stale resources from failed runs.

Interviewer

There are thousands of CI failures a day. Design a service that groups them so teams see 20 root causes, not 2,000 red tests.

What this tests The interviewer tests if you can design a data pipeline with normalization, grouping, idempotency and useful notifications.

Say this (30 seconds), then stop

CI sends JUnit results and logs through a webhook or artifact upload. An ingest API puts each run on a queue, so spikes do not overload the processing. Workers normalize each error message and stack trace, remove IDs and timestamps, and make a fingerprint. Same fingerprint means same group. Groups link to known issues. Full Staff-level answer

  1. 1. Ingest

    The shared workflow posts the JUnit XML and log location to an ingest API, or uploads them to S3. The API validates the request, stores the raw files and puts a message on a queue (SQS or Kafka). It answers fast, so CI never waits for processing.

  2. 2. Process idempotently

    Workers read from the queue. Each message has a key such as run ID plus test ID. If a message is delivered twice, the result is the same. Failed messages go to a dead-letter queue.

  3. 3. Normalize

    Remove noise from error messages and stack traces: UUIDs, timestamps, numbers, ports, temp paths and line numbers. Keep the error type, the message pattern and the top few stack frames.

  4. 4. Fingerprint and group

    Hash the normalized text to get a fingerprint. All failures with the same fingerprint are one group. Later, add fuzzy matching or embeddings to merge groups that are close.

  5. 5. Link and store

    Link groups to known issues, such as a Jira ticket or a quarantine entry. Store groups and occurrences in a database, for example PostgreSQL, with an index on fingerprint and time. Keep raw logs in S3.

  6. 6. Summarize and notify

    An optional LLM writes a short summary of each new group, from the normalized error and a sample log. It must quote the evidence and never guess a fix as fact. Notify only on new groups or groups that grow fast.

  7. 7. Use my experience

    At Joyent I built an experiment that used an LLM to analyze CI failures. It showed me that the LLM output is only as good as the input. Normalization and grouping must come first.

Webhooks vs polling vs queues

Interviewer

CI needs to react when a deploy to a downstream environment finishes. Do you use polling, webhooks or a queue?

What this tests The interviewer tests if you know integration patterns and their trade-offs in reliability, latency and cost.

Say this (30 seconds), then stop

Polling is simple but wastes calls and adds delay. A webhook pushes the event at once, but it needs a reachable endpoint, signature checks, retries and idempotency. A queue or pub/sub decouples the systems and buffers events, with retries and a dead-letter queue. For GitHub Actions, the deploy system can call repository_dispatch or workflow_dispatch when it finishes. For many consumers, I put an event bus in between.

Full Staff-level answer

  1. 1. State the need

    When the environment deploy finishes, the E2E suite must start against that version. The trigger must be fast, reliable, and secure.

  2. 2. Compare the options
    • Polling: CI asks "done yet?" every 30 seconds. Simple, but wasteful and slow.
    • Long-polling: the server holds the request until there is news. Fewer calls, but held connections.
    • Webhook: the deploy system calls a URL when it finishes. Fast, but needs a reachable endpoint and security.
    • WebSocket: a persistent two-way connection. Good for live UIs, too much for this.
    • Queue or pub/sub: the deploy system publishes an event. Consumers read it when ready.
  3. 3. Pick for GitHub Actions

    The deploy system calls the GitHub API: repository_dispatch with an event type and payload, or workflow_dispatch with typed inputs. GitHub is the endpoint, so we do not host one. Authenticate with a GitHub App token with minimal scope.

  4. 4. Pick for many consumers

    If several systems care about deploys, publish to an event bus such as EventBridge, SNS or Kafka. A small consumer triggers the GitHub workflow. The queue gives retries and a dead-letter queue.

  5. 5. Make it safe

    Verify webhook signatures. Make the handler idempotent with the deploy ID. Use a concurrency group per environment, so two deploys do not run E2E against a changing target.

Concepts you must own 9

Polling
Idea

The client asks again and again whether something changed.

Example

CI calls GET /deploys/123 every 30 seconds for up to 20 minutes.

Term

Simple and needs no inbound network. It wastes requests, adds up to one interval of delay, and can hit rate limits.

Long-polling
Idea

The client asks once, and the server waits to answer until there is news or a timeout.

Example

The request stays open up to 60 seconds and returns at once when the deploy ends.

Term

Fewer requests and lower delay than polling. The server holds many open connections. It is still a client pull.

Webhooks
Idea

The source system calls your URL when the event happens.

Example

The deploy tool sends POST /hooks/deploy with {env, version, status}.

Term

Push with low delay. It needs a public or reachable endpoint, HMAC signature verification, retries with backoff on the sender, and idempotent handlers.

Webhook signature verification
Idea

The receiver checks that the message really came from the sender and was not changed.

Example

GitHub sends X-Hub-Signature-256. The receiver computes HMAC-SHA256 with the shared secret and compares.

Term

Use a constant-time compare. Reject old timestamps to stop replay attacks.

Retries and idempotency for webhooks
Idea

Senders retry when they get no success answer, so the receiver can get the same event twice.

Example

The deploy tool retries after a timeout. The handler sees deploy ID d-77 again and ignores it.

Term

Store processed event IDs. Answer 2xx fast and do the work asynchronously.

WebSockets
Idea

A WebSocket is a long-lived, two-way connection between client and server.

Example

A live test dashboard gets each result the moment it finishes.

Term

Good for live UIs and chat. For a single "deploy done" event it adds connection management with no gain.

Message queues and pub/sub
Idea

A queue stores messages until a consumer reads them. Pub/sub sends one event to many subscribers.

Example

The deploy system publishes env-deployed. The E2E trigger, the release notes bot and the dashboard each get a copy.

Term

Benefits: decoupling, buffering of spikes, retries and a DLQ for failed messages. Examples: SQS (queue), SNS and EventBridge (pub/sub), Kafka (log).

Dead-letter queue (DLQ)
Idea

A DLQ holds messages that failed too many times, so they are not lost and do not block others.

Example

A malformed event fails 5 times and moves to the DLQ. An alarm tells the owner.

Term

SQS uses a redrive policy with maxReceiveCount. Monitor the DLQ depth.

repository_dispatch and workflow_dispatch
Idea

These are two ways to start a GitHub Actions workflow from outside GitHub.

Example

The deploy system calls POST /repos/ukg/e2e-suites/dispatches with event_type: env-deployed.

Term

repository_dispatch takes a custom event_type and a free client_payload, and runs on the default branch. workflow_dispatch targets one workflow and ref, with typed inputs, through POST /actions/workflows/{id}/dispatches.

Code to know

Follow-up questions

  • When is polling the correct choice?

    When the source cannot send events, when volume is low, or when the network does not allow inbound calls. Use a sensible interval with backoff and a timeout.

  • What if GitHub is down when the deploy finishes?

    With a direct call, the deploy system must retry. With a queue in between, the event waits in the queue and the consumer retries later. That is more reliable.

  • How do you secure repository_dispatch?

    Use a GitHub App with only the permission it needs on the target repo. Do not use a personal access token. Validate the payload in the workflow before you use it.

Caution
  • Some candidates say "webhooks are always better". Webhooks need security, retries and idempotency, or events get lost or repeated.
  • Some candidates use a sleep 600 in CI to wait for the deploy. That is slow and still fails when the deploy takes longer.
  • Some candidates trust the webhook payload without a signature check. Anyone can then start pipelines.

UKG-L1

A team refuses to migrate

Interviewer

A large, influential team says the Playwright migration is a waste of time and refuses to do it. What do you do?

What this tests The interviewer tests if you can influence a strong team without authority and without a fight.

Say this (30 seconds), then stop

First I listen, because they may have a real cost or constraint that I do not see. Then I show their own data, such as flaky rate and pipeline time, not general claims. I offer help: pairing, codemods and migration tooling, so the cost for them is small. If they still have a good reason, I agree an exception with an end date. I escalate only with a clear trade-off for leadership, not as a complaint.

Full Staff-level answer

  1. 1. Understand their position

    Meet the tech lead and ask about their costs and constraints. Maybe they have a release deadline, a huge suite, or a bad experience with an earlier migration. Write down their concerns and confirm them back.

  2. 2. Show their own data

    Bring numbers about their suites: flaky rate, pipeline time, time spent on test maintenance. Compare with a pilot team that already migrated. Data about their own work is stronger than a general argument.

  3. 3. Make the migration cheap

    Offer pairing for the first suites, codemods and LLM-assisted conversion, and a migration guide. Make the new path the easy path: better reports, faster runs, and shared fixtures that remove their custom code.

  4. 4. Agree on a plan that fits them

    Start with their most painful suite, where the gain is fastest. Fit the work around their release dates.

  5. 5. Allow an exception with an end date

    If the timing is truly bad, agree an exception with a date and a condition. Write it down, so it does not become permanent.

  6. 6. Escalate only as a trade-off

    If there is still no agreement, write a short note for both sets of leaders. It states the options, the cost of each, and my recommendation. Leadership then decides the trade-off. It is not a complaint about the team.

You became the bottleneck

Interviewer

Every framework change needs your review, and 20 teams are waiting on you. How do you fix this?

What this tests The interviewer tests if you scale yourself through systems and people instead of more effort.

Say this (30 seconds), then stop

I replace my review with written standards and automated checks such as lint and CI. Big changes go through a short RFC or ADR process, so decisions do not depend on me. Full Staff-level answer

  1. 1. Find out what I really review

    Look at the last 50 reviews. Group them: style, correctness, API design, risk. Most are usually small and repeatable, so a tool or a document can handle them.

  2. 2. Turn rules into automation

    Write the standards down. Turn the repeatable ones into lint rules, type checks, tests and CI gates. Then a pull request gets fast feedback without me.

  3. 3. Use a light RFC or ADR process for big changes

    A short template: problem, options, decision, consequences. Review happens in writing, with a time limit. Recorded decisions mean people do not need to ask me again.

  4. 4. Spread ownership

    Set CODEOWNERS by area, with two or more owners each. Choose trusted contributors from other teams. Pair-review with them at first, then let them review alone.

  5. 5. Remove the need for core changes

    Add extension points such as plugins, custom fixtures and reporters. Teams can then build what they need in their own repos.

  6. 6. Measure the result

    Track review wait time and the share of reviews that I do. My target is to review only the high-risk changes.

Disagree with a Principal engineer

Interviewer

Full Staff-level answer

  1. 1. Understand the goal

    Ask what the custom framework must do that Playwright cannot. Maybe it is control over the roadmap, a special protocol or a security rule. That need may be real, and it changes the design.

  2. 2. Agree on criteria first

    Agree on the criteria before the options: maintenance cost, hiring and onboarding, ecosystem, time to value, and risk. When people agree on criteria, the decision often becomes clear.

  3. 3. Get evidence

    Propose a time-boxed spike, for example two weeks. Build the hardest real scenario both ways. Measure effort, stability and debugging time.

  4. 4. Write the trade-off document

    Show the options, the evidence, the costs and the risks, including the risks of my own option. Share it with the Principal first, then with the wider group.

  5. 5. Disagree and commit

    When the decider decides, I support the decision in public and in my work. If new evidence appears later, I bring it back through the same process.

    Talk in private before public meetings. Give credit for good points. The goal is the best result for the teams, not winning.

Release blocked at 6 PM

Interviewer

It is 6 PM before a launch. The automation suite is red and blocks the release. Product wants you to skip the failing suite. What do you do?

What this tests The interviewer tests if you can make a fast, risk-based call with the right people and a clear process.

Say this (30 seconds), then stop

I triage fast: is it a real bug, a flaky test, or an infra problem? Traces, failure history and a re-run on the same build usually tell me in 15 minutes. I do not make the call alone. I bring the risk to the release owner and the engineering owner, and we use the documented override policy with sign-off. Known-flaky tests go into quarantine with a ticket. After the launch, we hold a postmortem and fix the cause.

Full Staff-level answer

  1. 1. Triage fast

    Look at which tests fail and why. Check the failure history: did these tests fail before on green builds? Check infra: runner, grid, environment health. Re-run the failed tests one time on the same build.

  2. 2. Classify
    • Real bug: the release waits, or the feature is turned off with a flag.
    • Flaky test: known flaky, with history. It can be quarantined.
    • Infra: fix or re-run on healthy infra.
  3. 3. Make a risk-based call with owners

    Bring the facts to the release owner and the engineering owner of the area. Explain what the failing tests cover and what the risk is. The owners decide, using the override policy.

  4. 4. Follow the override policy

    An override needs named sign-off, a written reason and a follow-up ticket. Add manual checks for the uncovered area if needed. Record it, so it is visible later.

  5. 5. Quarantine, do not delete

    Move known-flaky tests to a quarantine list with an owner and a due date. They still run and report, but they do not block.

  6. 6. Learn

    Hold a short postmortem after the launch. Fix the root cause, and check why the problem appeared so late in the cycle.

Teams add one small caller file that uses a versioned reusable workflow. The workflow runs fast checks on ephemeral ARC runners inside the VPC. Full Staff-level answer

  1. 1. Clarify requirements first

    Ask and state assumptions:

    • 200 teams, a mix of Selenium today and Playwright tomorrow, plus API tests.
    • Peak of about 2,000 parallel browser sessions at 9 AM, near zero at night.
    • Test environments live in private VPCs.
    • Goals: PR feedback under 10 minutes, flaky rate down, cost visible per team.
    • Constraints: security review, existing Jenkins or Selenium suites, team autonomy.
  2. 2. Orchestration with GitHub Actions

    A platform repo holds reusable workflows (on: workflow_call) and composite actions, released with SemVer tags. Teams keep an 8-line caller file. An org ruleset requires the shared workflow on protected branches. Tiers: smoke on PR, full suite on merge, cross-browser nightly. Concurrency groups cancel old runs on the same PR.

  3. 3. Runners and execution on EKS

    Two layers of compute:

    • CI runners: Actions Runner Controller with runner scale sets in the VPC. Each job gets an ephemeral runner pod.
    • Browser farm: the runner splits the suite into shards and puts them on an SQS queue. A KEDA ScaledJob creates one Playwright Job per shard. Selenium Grid 4 runs beside it during the migration.

    Karpenter adds Spot nodes in a tainted browsers NodePool with a CPU limit. Each team has a namespace with a ResourceQuota.

  4. 4. Framework distribution and versioning
    • @ukg/test-core: Playwright fixtures, test data builders, loginAs, reporters.
    • @ukg/test-api: the API client with REST, SOAP and GraphQL adapters.
    • A worker image with pinned browsers, tagged with the framework version and commit SHA.

    Packages live in a private registry such as CodeArtifact or GitHub Packages. SemVer, deprecation windows, canary consumers for each RC, and Renovate PRs keep teams current.

  5. 5. Results pipeline

    Each worker writes JUnit, a JSON summary and traces. Large files go to S3 with lifecycle rules. The summary goes to a results ingest API, which puts it on a queue. Workers normalize failures, fingerprint them, group them and store them in PostgreSQL. The CI job reads the final status and writes a job summary.

  6. 6. Observability and cost controls

    Grafana dashboards per audience: flaky rate, pipeline time p50 and p90, queue time, failure classes, adoption and version spread. Prometheus and Container Insights watch the cluster: Pending pods, node pressure and free subnet IPs. Slack alerts go out only on state change and new failure groups. The platform has its own SLOs, for example queue time under 2 minutes at p90. Cost controls:

    • Scale to zero overnight with KEDA and Karpenter consolidation.
    • Spot for retryable test shards, On-Demand for shared services.
    • NodePool limits and per-team quotas as hard ceilings.
    • Test impact selection so a PR runs only the affected tests.
    • Cost per team from pod labels and AWS split cost allocation data, shown on the dashboard.
  7. 7. Security
    • GitHub to AWS: OIDC with id-token: write and trust policies scoped to repo, branch or environment.

    • Runners: ephemeral, in runner groups limited to private repos, never for fork PRs.
    • Supply chain: actions pinned to SHAs, signed images, secret scanning and push protection.

    Make the platform the easy path: one file to adopt, faster runs, better reports and less maintenance. Start with pilot teams and publish their before and after numbers. Offer migration tooling, office hours and pairing. Track adoption on a dashboard, and agree exceptions with end dates.

Data flow

  1. A developer opens a PR. The caller workflow starts the shared reusable workflow at @v3.
  2. GitHub assigns the job to the e2e-private runner scale set. ARC creates an ephemeral runner pod in EKS.
  3. The job gets an OIDC token. AWS STS returns short-lived credentials for the submit role.
  4. The job runs lint, unit and API tests on the runner pod.
  5. The job splits the E2E suite into shards and sends one SQS message per shard.
  6. KEDA sees the queue length and creates one Playwright worker Job per shard.
  7. Pending worker pods trigger Karpenter. It starts Spot nodes in the browsers NodePool.
  8. Each worker pulls its image from ECR, gets test credentials from Secrets Manager through Pod Identity, and runs its shard against the private test environment.
  9. Each worker uploads traces and reports to S3 and posts a JSON summary to the results ingest API.
  10. The ingest API puts the summary on the results queue. Triage workers normalize, fingerprint and group failures, and write to PostgreSQL.
  11. The CI job polls the results API until all shards finish. Then it writes the job summary and passes or fails the check.
  12. The results service compares the state with the last run. On a change or a new failure group, the Slack app posts to the team channel.
  13. Grafana reads PostgreSQL and Prometheus for the dashboards. Alerts fire on trend changes and on platform SLO breaches.

Selenium

Explain the Selenium WebDriver architecture.

Your test code uses a language binding, for example the Java client. The binding sends W3C WebDriver commands over HTTP to a driver, for example chromedriver. The driver controls the real browser. Each command is a request, and the driver sends a response. Selenium 4 uses the W3C WebDriver standard, so all major browsers speak the same protocol. Selenium also moves to WebDriver BiDi. BiDi adds a WebSocket so the browser can send events, for example console logs and network requests.

Which locator strategy do you prefer and why?

Use a stable, unique attribute first. A dedicated test attribute such as data-testid is the best choice. Then use id or name if they are stable. Use CSS selectors before XPath, because CSS is short and fast to read. Use XPath only when you must find an element by its text or by a parent. Do not use absolute XPath or index-based locators. They break when the layout changes.

Explain implicit, explicit and fluent waits.

An implicit wait is a global timeout for findElement. An explicit wait (WebDriverWait) waits for one condition on one element, for example "clickable". A fluent wait is an explicit wait with a custom poll interval and a list of exceptions to ignore. Use explicit waits. Do not mix implicit and explicit waits. If you mix them, the timeouts can add up and the wait time becomes hard to predict. Never use Thread.sleep as a wait.

What is the Page Object Model? What is Page Factory?

The Page Object Model puts the locators and actions of one page in one class. Tests call methods such as loginPage.login(user). They do not touch locators directly. When the UI changes, you change one class, not many tests. Page Factory is a Selenium helper that fills @FindBy fields with lazy proxies. Many teams now prefer plain page objects with By locators and explicit waits, because Page Factory proxies can hide stale-element problems.

What causes StaleElementReferenceException and how do you fix it?

The driver keeps a reference to one DOM node. If the page re-renders that node, the old reference becomes stale. A click on the old reference then fails. To fix it, find the element again just before you use it. Wait for the re-render to finish with an explicit wait. Store By locators, not WebElement objects, in page objects.

How do you handle iframes, windows and alerts?

  • iframe: call driver.switchTo().frame(...) before you find elements inside it. Call switchTo().defaultContent() after.
  • New window or tab: get getWindowHandles(), then switchTo().window(handle). Selenium 4 also has switchTo().newWindow(WindowType.TAB).
  • JavaScript alert: wait with ExpectedConditions.alertIsPresent(). Then call accept(), dismiss() or getText().

Explain Selenium Grid 4 components.

Grid 4 splits the old hub into parts that can run alone:

  • Router: the entry point. It sends new-session requests to the queue and other requests to the correct Node.
  • New Session Queue: holds new-session requests in FIFO order.
  • Distributor: knows all Nodes and their capabilities. It takes requests from the queue and gives each one to a Node.
  • Session Map: maps a session ID to the Node that runs it.
  • Event Bus: carries messages between the parts.
  • Node: runs browsers and manages slots.

You can run Grid in standalone, hub-and-node, or fully distributed mode.

What is Selenium Manager?

Selenium Manager ships with Selenium since version 4.6. It finds, downloads and caches the correct driver for your browser. Since 4.11 it can also download Chrome for Testing, and later Firefox and Edge. You do not need WebDriverManager or manual driver paths in most cases. The Selenium docs still mark it as beta. Grid can use it with --selenium-manager true.

How do you run Selenium tests in parallel safely?

Give each test thread its own WebDriver. Keep the driver in a ThreadLocal. Do not share static driver fields. Use unique test data per test. Set TestNG parallel="methods" or "classes" and a thread-count. Run browsers on a Grid or in containers so the machine does not run out of resources.

Playwright

Explain the Playwright architecture.

The test runner talks to the browser through one persistent connection. It does not send one HTTP request per command as classic WebDriver does. Playwright uses CDP for Chromium and its own patched protocols for Firefox and WebKit. Playwright downloads browser builds that match each release. One browser process can hold many browser contexts. Each context is like a new, clean browser profile.

What is auto-waiting and actionability?

Before an action, Playwright checks that the element is ready. For a click, it waits until the element is attached, visible, stable, enabled and able to get events. If a check fails, Playwright retries until the timeout. Web-first assertions such as expect(locator).toBeVisible() also retry. Because of this, you do not need manual waits in most tests.

Which locators does Playwright recommend?

Use locators that match what a user sees. Prefer getByRole with an accessible name, for example getByRole('button', { name: 'Save' }). Use getByLabel, getByPlaceholder and getByText for forms and content. Use getByTestId when there is no good user-facing locator. Use CSS or XPath only as a last choice. Locators are lazy and strict: an action fails if the locator matches more than one element.

What are browser contexts and why do they matter?

A browser context is an isolated session with its own cookies, storage and cache. Playwright Test gives each test a new context. Tests do not share state, so they can run in parallel. A new context is much faster than a new browser. You can open two contexts in one test to test two users at the same time.

What are fixtures in Playwright Test?

A fixture gives a test something that it needs, for example page, context or request. You can write custom fixtures for a logged-in page, a test user or an API client. A fixture runs setup before the test and teardown after it. Tests ask for fixtures by name, so setup is shared without base classes. For a framework team, custom fixtures are the main public surface that other teams use.

How do workers, parallelism and sharding work?

Playwright runs test files in parallel worker processes. Set the count with workers. Set fullyParallel: true to run tests inside one file in parallel too. Sharding splits the suite across machines with --shard=1/4. With fullyParallel, shards split by test, so they are more even. Use the blob reporter on each shard, then npx playwright merge-reports to make one HTML report.

How do you handle flaky tests and debug failures (retries, trace viewer, UI mode)?

Set retries in the config, for example 2 in CI. A test that fails and then passes is marked "flaky" in the report. Track the flaky count over time. Use --fail-on-flaky-tests when flakiness must block a run. Set trace: 'on-first-retry' to record actions, DOM snapshots, network and console for a retried test. Open the trace in the HTML report or with npx playwright show-trace. Use UI mode (--ui) to run and step through tests. Use --last-failed to run only the tests that failed in the previous run.

How do you mock or intercept network calls?

Use page.route(urlPattern, handler). In the handler, call route.fulfill() to return fake data, route.abort() to block, or route.continue() to change and pass the request. Mock only to test UI states that are hard to create, for example errors. Keep some tests against the real backend, so that the mocks do not hide contract changes.

How do you test APIs and reuse login with Playwright?

The request fixture gives an APIRequestContext. Use it to call REST APIs directly, for API tests or for fast test setup. For login, run a setup project once. Save cookies and local storage with context.storageState({ path }). Other projects load that file with use: { storageState }, so tests start logged in.

Compare Playwright, Selenium and Cypress.

  • Selenium: W3C standard, many languages, very large ecosystem, Grid for scale. You must build waits, reports and fixtures yourself.
  • Cypress: runs inside the browser, very good developer experience, JavaScript/TypeScript only. Multi-tab and multi-origin support is more limited.
  • Playwright: auto-wait, contexts, tracing, sharding and API testing built in. It supports TypeScript/JavaScript, Java, Python and .NET.

For a new platform, Playwright gives most features out of the box. Selenium still fits large Java suites that already exist.

Java test stack: Maven, TestNG, JUnit 5

Explain the Maven build lifecycle.

The default lifecycle runs phases in order. The main phases are validate, compile, test, package, verify, install and deploy. When you run a phase, Maven runs all earlier phases first. Plugins attach goals to phases. For example, Surefire attaches to test. mvn clean verify is a common CI command.

What is the difference between Surefire and Failsafe?

Surefire runs unit tests in the test phase. By default it finds classes named *Test. Failsafe runs integration tests in the integration-test phase and checks results in verify. By default it finds classes named *IT. Failsafe lets post-integration-test run even when tests fail, so cleanup can happen. Put E2E and API tests in Failsafe.

Compare TestNG and JUnit 5.

  • Annotations: TestNG has @BeforeSuite, @BeforeTest, @BeforeClass, @BeforeMethod. JUnit 5 has @BeforeAll, @BeforeEach.
  • Grouping: TestNG uses groups. JUnit 5 uses @Tag.
  • Data-driven: TestNG uses @DataProvider. JUnit 5 uses @ParameterizedTest with sources.
  • Parallel: TestNG sets it in testng.xml. JUnit 5 sets it in junit-platform.properties.
  • Dependencies: TestNG has dependsOnMethods. JUnit 5 does not, by design.

TestNG is common in Selenium suites. JUnit 5 is common in new Java projects.

Write a TestNG data provider.

A data provider returns rows of arguments. TestNG runs the test once for each row. Set parallel = true on the provider to run rows in parallel.

Why use ThreadLocal for WebDriver?

In parallel runs, many threads run tests at the same time. If they share one static driver, one test can click in another test's browser. ThreadLocal gives each thread its own driver instance. Always call remove() after quit(). If you do not, thread pools can reuse an old driver.

How do you manage dependency versions in a shared test framework?

Publish the framework as a versioned artifact. Use a BOM (dependencyManagement) so that consumers get compatible versions of Selenium, TestNG and REST Assured together. Pin plugin versions. Use mvn dependency:tree to find conflicts. Let Renovate or Dependabot open update pull requests, and let CI test them.

Which Java collection fits an in-memory cache?

Use ConcurrentHashMap for a thread-safe key-value cache. Collections.synchronizedMap locks the whole map on each call, so it is slower under load. For a size-limited LRU cache, extend LinkedHashMap with access order and override removeEldestEntry. For production caches, a library such as Caffeine gives expiry and eviction.

API testing

Compare REST, SOAP and GraphQL.

  • REST: resources and HTTP verbs. Status codes tell the result. The payload is usually JSON.
  • SOAP: an XML envelope with a WSDL contract. Errors come as SOAP faults. It usually uses HTTP POST.
  • GraphQL: one endpoint. The client asks for the exact fields that it needs. Errors often come in an errors array with HTTP 200.

A test layer must check GraphQL errors and SOAP faults. A status code check alone is not enough.

Which HTTP status codes must you know?

  • 200 OK, 201 Created, 204 No Content.
  • 301/302 redirect, 304 Not Modified.
  • 400 Bad Request, 401 Unauthorized (no valid identity), 403 Forbidden (identity known, no permission), 404 Not Found, 409 Conflict, 422 Unprocessable Entity, 429 Too Many Requests.
  • 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout.

What is idempotency?

A request is idempotent when many identical calls have the same effect as one call. GET, PUT and DELETE are idempotent. POST is not idempotent by default. Many APIs accept an idempotency key so that a retried POST does not create a duplicate. Test this: send the same request twice and check that the system has one record.

Show a REST Assured test.

REST Assured uses a given/when/then style. given sets headers, auth and body. when sends the request. then checks the status and the body.

What is consumer-driven contract testing?

The consumer writes tests that state what it needs from the provider. Pact records these needs as a contract file. The provider runs the contract against its real code in its own CI. If the provider breaks the contract, its build fails before deploy. Contract tests are faster and more stable than full E2E tests between services.

When do you mock an API with WireMock?

Mock a dependency when it is slow, costly, unstable or not built yet. Mock it also to create hard cases, for example a timeout or a 500 error. WireMock runs a fake HTTP server with stubbed responses. Do not mock everything. Keep a smaller set of tests against real services, so that mocks do not drift from reality.

Explain the test pyramid.

Have many fast unit tests at the bottom. Have fewer service and API tests in the middle. Have a small number of slow UI E2E tests at the top. Most checks belong in lower layers, where they are fast and stable. Use E2E tests for the main user journeys only. For a platform team, the pyramid guides where to spend framework effort.

Explain OAuth2 and JWT for test automation.

OAuth2 is a protocol to get an access token. Test suites often use the client-credentials flow, because there is no user in the loop. A JWT is a signed token with three parts: header, payload (claims) and signature. The server checks the signature and the expiry. In tests, get a token once per run, cache it, and refresh it before it expires. Never print tokens in logs.

AWS basics

Explain IAM users, roles and policies.

A user is a long-term identity for a person or app. A role is an identity that has no long-term keys. Something assumes the role and gets temporary credentials from STS. A policy is a JSON document that allows or denies actions on resources. A trust policy on a role says who can assume it. Prefer roles with temporary credentials for CI and for pods.

Explain a VPC with public and private subnets.

A VPC is your private network in AWS. A public subnet has a route to an internet gateway. A private subnet has no direct route from the internet. Resources in a private subnet use a NAT gateway for outbound internet access. EKS worker nodes and test runners usually run in private subnets. Load balancers for public traffic run in public subnets.

Compare security groups and network ACLs.

A security group is a stateful firewall on an ENI, for example an EC2 instance. It has allow rules only. Return traffic is allowed automatically. A network ACL is a stateless firewall on a subnet. It has allow and deny rules, and you must allow return traffic yourself. Most teams use security groups as the main control.

What are S3 and ECR used for in a test platform?

S3 stores objects, for example test reports, screenshots, videos and traces. Use lifecycle rules to delete old artifacts and control cost. ECR is the AWS container registry. Store test-runner and browser images there. Pull from ECR inside AWS to avoid Docker Hub rate limits.

Compare ALB and NLB.

An ALB works at layer 7 (HTTP/HTTPS). It routes by host and path, and it can end TLS. An NLB works at layer 4 (TCP/UDP). It is very fast and can keep static IPs. On EKS, the AWS Load Balancer Controller creates an ALB for an Ingress. It creates an NLB for a Service of type LoadBalancer.

What is CloudWatch?

CloudWatch collects metrics and logs from AWS services and apps. You can make dashboards and alarms on metrics. CloudWatch Logs Insights lets you query logs. Container Insights adds cluster, node and pod metrics for EKS.

Compare EC2 and Fargate for running tests.

On EC2, you manage the instances, and you pay for them while they run. You get full control, for example over /dev/shm size, GPUs and DaemonSets. Fargate runs each pod or task on its own managed compute, and you pay per pod. Fargate is simple, but it has limits, for example no DaemonSets. Browser-heavy test fleets often use EC2 nodes with Karpenter and spot instances.

Docker

What is the difference between an image and a container?

An image is a read-only template. It has the file system and the start command. A container is a running instance of an image with a thin writable layer on top. You can start many containers from one image. When you delete a container, its writable layer goes away.

How do layers and the build cache work?

Each Dockerfile instruction makes a layer. Docker reuses a cached layer if the instruction and its inputs did not change. A change to one layer rebuilds that layer and all layers after it. So put steps that change rarely first, for example dependency install. Put steps that change often last, for example COPY of source code.

What is a multi-stage build?

A multi-stage build uses one stage to build and a second stage to run. The final image copies only the build output from the first stage. Build tools and source code stay out of the final image. The image becomes smaller and has fewer vulnerabilities.

Name Dockerfile best practices.

  • Use a small, trusted base image with a pinned version.
  • Copy the dependency file first, install, then copy source code.
  • Use multi-stage builds.
  • Run as a non-root user.
  • Add a .dockerignore file.
  • Do not put secrets in the image or in build arguments.
  • Combine related RUN steps and clean package caches in the same step.

What is the difference between an image tag and a digest?

A tag is a name, for example app:1.4.0 or latest. Someone can move a tag to a different image. A digest (sha256:...) is the hash of the image content. A digest never changes. Deploy and promote by digest, so that staging and production run the exact same image.

How does Docker Hub rate limiting affect CI?

Docker Hub limits pulls in a 6-hour window. Unauthenticated pulls get 100 per IPv4 address or IPv6 /64. Authenticated Personal accounts get 200. Pro, Team and Business accounts are unlimited under fair use. Many CI runners can share one IP and hit the limit. To fix it, log in for pulls, use a pull-through cache, or mirror images to ECR.

CI/CD fundamentals

What is the difference between continuous integration, continuous delivery and continuous deployment?

Continuous integration means that developers merge small changes often, and CI builds and tests each change. Continuous delivery means that every change that passes is ready to release, but a person starts the production release. Continuous deployment means that every change that passes goes to production automatically. Each step needs more trust in the tests.

What are typical pipeline stages?

  1. Checkout and install dependencies (with cache).
  2. Lint and static analysis.
  3. Unit tests.
  4. Build the artifact or image once, and tag it with the commit SHA.
  5. Security scan.
  6. Deploy to a test environment.
  7. API and E2E tests.
  8. Promote the same artifact to staging, then production, with approvals.

How do you handle flaky tests in CI?

First, measure. A test that fails and then passes on retry is flaky. Record each retry. Move a known-flaky test to a quarantine group. The quarantine group still runs, but it does not block merges. Give each quarantined test an owner and an end date. Fix the cause: waits, shared data, test order or environment. Then return the test to the main group.

What is trunk-based development?

Developers merge small changes into one main branch often, at least daily. Branches live for a short time. Unfinished features hide behind feature flags. This needs fast and reliable CI, because main must stay green. Long-lived branches cause large merges and late test failures.

How do feature flags affect testing?

A feature flag turns code on or off without a deploy. Tests must cover the important flag states, not only the default. Set flag values per test or per environment in a controlled way. Remove old flags, because each flag adds test combinations.

Compare Jenkins and GitHub Actions.

  • Jenkins: self-hosted server, Groovy pipelines, very many plugins. You manage upgrades, security and agents.
  • GitHub Actions: YAML workflows next to the code, events from GitHub, a marketplace of actions, and hosted or self-hosted runners.
  • Actions has reusable workflows, OIDC to clouds and environments with approvals built in.

Observability

What are logs, metrics and traces?

Logs are records of single events with details. Metrics are numbers over time, for example request rate or test pass rate. They are cheap to store and good for alerts. Traces follow one request across services as a tree of spans. Use metrics to find that something is wrong. Use traces to find where. Use logs to find why.

How do Prometheus and Grafana work together?

Prometheus pulls (scrapes) metrics from /metrics endpoints on a schedule. It stores them as time series with labels. You query them with PromQL. Alertmanager sends alerts from Prometheus rules. Grafana connects to Prometheus and other sources and shows dashboards.

Explain SLI, SLO and error budget.

An SLI is a measured value, for example the percent of CI runs that finish in under 10 minutes. An SLO is the target for that SLI, for example 95 percent over 28 days. The error budget is the allowed miss, here 5 percent. When the budget is used up, the team works on reliability before new features. An SLA is a contract with a customer, and it usually has a lower target than the SLO.

What is OpenTelemetry?

OpenTelemetry is an open standard and a set of SDKs for traces, metrics and logs. Apps send data in the OTLP format to an OpenTelemetry Collector. The collector processes the data and sends it to a backend, for example Prometheus, Jaeger or a vendor tool. You do not lock your code to one vendor.

Which metrics show the health of a test platform?

  • Pass rate and flaky rate per suite and per team.
  • Queue time and run time (p50 and p95).
  • Failure classes: product bug, test bug, infrastructure.
  • Time to diagnose a failure.
  • Adoption: number of teams and framework version spread.
  • Cost per run.

Alert on trends, not on each single failure.

System design (platform-focused)

What are micro-frontends?

A micro-frontend architecture splits one web UI into parts that different teams build and deploy alone. A shell app loads the parts at runtime, for example with Module Federation. Each team owns its part from end to end. Shared design-system components keep the UI consistent. The risks are larger bundles, version conflicts and harder E2E tests across parts.

What is event-driven architecture?

Services publish events when something happens, for example "test run finished". Other services subscribe and react. The publisher does not know the subscribers. This decouples teams and lets you add consumers without changes to the publisher. You must handle duplicate events, event order and schema changes.

Where do you use caching, and what are the risks?

Use a cache to keep the results of slow or frequent reads, for example in Redis or in memory. Common patterns are cache-aside (read the cache, on a miss read the database and fill the cache) and write-through. Set a TTL on each entry. The main risks are stale data and a large load on the database when many entries expire at the same time.

How does rate limiting work?

A rate limiter caps how many requests a client can make in a time window. Common algorithms are token bucket, leaky bucket, fixed window and sliding window. A token bucket allows short bursts and keeps a steady average. When a client is over the limit, return HTTP 429 with a Retry-After header. In a cluster, keep the counters in a shared store such as Redis.

Why put a queue between services?

A queue buffers work between a producer and a consumer. The producer stays fast when the consumer is slow or down. You can scale consumers on queue depth. Failed messages go to a dead-letter queue after a set number of retries. Consumers must be idempotent, because most queues deliver a message at least once.

Coding problems likely for this role

Parse a log file and count errors by type.

Read the file line by line. Use a regular expression to find lines with ERROR and get the error type. Count each type in a map. Sort the map by count, high to low. The time is O(n) for the scan plus O(k log k) for the sort.

Group CI failures by root cause (normalize and dedupe).

Make a fingerprint for each failure message. Replace numbers, IDs, UUIDs and timestamps with placeholders. Use the result as a map key. Put each test name into the list for its key. Sort groups by size so that the biggest root cause comes first.

Retry an operation with exponential backoff.

Call the operation. If it fails, wait and try again. Double the wait after each failure, up to a maximum. Add random jitter so that many clients do not retry at the same time. Stop after a set number of attempts and throw the last error. Retry only errors that can be temporary.

Write a polling wait helper (wait until a condition is true).

Check the condition. If it is true, return. If not, sleep for the poll interval and check again. Stop with a clear error when the timeout passes. Include the last value in the error message, so that the failure is easy to diagnose.

Deep-merge two config objects (defaults plus overrides).

Start with a copy of the defaults. For each key in the overrides: if both values are plain objects, merge them recursively. In all other cases, the override value wins. Arrays are replaced, not merged. Do not change the input objects.

Longest substring without repeating characters (sliding window).

Keep a window with a left and a right pointer. Move right one step at a time. Keep the last index of each character in a map. If the character is already in the window, move left past its last index. Record the largest window size. The time is O(n).

Check if a string is a palindrome (two pointers).

Put one pointer at the start and one at the end. Skip characters that are not letters or digits. Compare the characters without case. Move the pointers toward the center. If two characters are different, return false. The time is O(n) and the space is O(1).

Reverse a linked list.

Keep three references: previous, current and next. For each node, save the next node. Point the current node back to the previous node. Then move previous and current one step forward. At the end, previous is the new head. The time is O(n) and the space is O(1).

Binary tree: root-to-leaf path sum, and level-order traversal (BFS).

Path sum: subtract the node value from the target as you go down. At a leaf, check if the rest is zero. Use recursion (DFS). Level order: use a queue. Take all nodes of the current level from the queue, record their values, and add their children. A UKG Noida report asked the path-sum problem.

Print the prime numbers from 1 to N efficiently.

Use the Sieve of Eratosthenes. Mark all numbers as prime at the start. For each prime p, starting at 2, mark p*p, p*p+p and so on as not prime. Stop when p*p is larger than N. The time is O(N log log N). A UKG Noida report asked this for N = 200.
